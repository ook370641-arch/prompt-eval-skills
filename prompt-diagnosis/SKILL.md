# Prompt 诊断 Skill

## Soul：人机协作模式

这个 Skill 的协作方式不是"用户下指令，AI 执行"，而是：

**AI 先诊断prompt问题 → 分析bad case（如有） → 输出诊断报告 → 说出打算落实的修改行动 → 提问收集缺失信息 → 用户确认调整策略 → AI调用子agent写新prompt → 检验新prompt质量 → 输出测试建议与最终交付物**

模型不仅是执行者，也可以是帮助用户暴露问题、协助拆解任务的对象。

**关系翻转**：让大模型作为输入方，向你提问，抓取那些为了修改prompt所需的信息。

**核心理念**：Prompt 是任务设计的"结果"，不是任务设计本身。从"改措辞"转向"做任务建模"。

---

## 目标

诊断Prompt质量，分析bad case，对齐调整策略，产出新Prompt。交付物是Prompt报告（诊断+测试建议）+ 新Prompt。

---

## 何时使用

- 改了一条规则，但输出其他部分也一起漂移
- 同类 bad case 在多轮 Prompt 下依然随机波动，需要可靠的评测规划
- 不确定该继续调 Prompt，还是该改规则、拆阶段
- 需要检验一个提示词是否足够清晰

| 层级          | 要求    | 描述                   | 任务系统拆解 | 错误归因                  |
| ----------- | ----- | -------------------- | ------ | --------------------- |
| **A 任务定义层** | 目标/标准 | 定义目标、好坏标准、失败定义、优先级   | 定义问题   | 目标不清、标准模糊、优先级冲突       |
| **B 任务拆分层** | 流程/任务 | 拆分子任务、判断是否需要分阶段      | 结构问题   | 任务耦合、一步塞太多、局部修改引发全局漂移 |
| **C 规则下沉层** | 规则/执行 | 把需求下沉成可判断、可排序、可执行的规则 | 执行问题   | 规则未下沉、规则间缺少优先级、执行不稳定  |

#### A层：任务定义层检验

| 检验项  | 检验问题                      | 通过标准                 |
| ---- | ------------------------- | -------------------- |
| 目标   | 模型最终要产出什么？输出形式、字段、格式是否明确？ | 有具体输出形式（JSON/文本/列表）  |
| 好坏标准 | 什么算对，什么算错？是否有具体判定条件？      | 有具体判定条件，不是"效果好"这种模糊词 |
| 失败定义 | 哪些情况可以接受失败或放弃输出？          | 有明确的失败场景定义           |
| 优先级  | 当有冲突时，优先保什么？              | 有明确的取舍原则             |

**A层问题典型现象**：要求含糊、抽象、多义；标准不清；优先级不明

#### B层：任务拆分层检验

| 检验项  | 检验问题                    | 通过标准         |
| ---- | ----------------------- | ------------ |
| 输入   | 上游能提供什么输入？哪些可用、哪些不可用？   | 明确输入边界       |
| 输出   | 下游需要哪些字段？哪些是生产必须、哪些是调试？ | 区分了生产字段和调试字段 |
| 拆分决策 | 是否需要拆成多阶段？还是单 Prompt？   | 有明确决策        |

**B层问题典型现象**：改一个局部，整体都飘；一步塞太多内容

#### C层：规则下沉层检验

| 检验项   | 检验问题               | 通过标准                |
| ----- | ------------------ | ------------------- |
| 边界    | 哪些内容属于处理对象？哪些必须排除？ | 有包含/排除标准            |
| 红线    | 有哪些绝对不能做的事？        | 有禁止项列表或明确无禁止        |
| 规则    | 有哪些必须遵守的具体规则？      | 有可执行描述，不是"要准确"这种模糊词 |
| 规则优先级 | 规则之间有优先级吗？冲突时怎么处理？ | 有规则排序               |
| **入参咬合** | **站在模型视角，它实际收到的入参撑得起这些规则要它做的判定吗？** | **每条规则要的证据，入参里都真实存在、够用、可核验** |

**C层问题典型现象**：模型常常"理解对了但输出不稳"；某条规则看起来没生效

**入参咬合检验（C层的深化，必做）**：

> 为什么并进 C 层：一条规则"可执行"的前提，是模型能**依据提示词对它实际收到的入参做处理**。规则要的证据入参里根本没有，这条规则再清晰也执行不了——病根在 C 层。

**站在模型的角度**（不是站在你的角度）走三步：

1. **先看模型实际拿到什么入参**——不是你以为它有什么，是它真正收到的：标题、ASR/字幕、画面、检索片段、结构化字段……逐一列出。
2. **再看每条判据要什么证据**——把"判 X / 排除 Y"的每条触发条件，问一句：它要的证据，入参里有没有、够不够、可不可核验？
3. **对不上的地方就是病灶**：
   - 判据要的证据入参根本没有（如"看开篇字幕是否点题"但入参只有 ASR、无画面帧）→ 规则悬空，模型只能瞎猜/走过场。
   - 入参有脏/空/噪声（ASR 错乱、字段为空）却被判据当可信证据用 → 模型被带偏。
   - 判据是纯主观自评（"是否高效/是否卓越"），不落任何可核验入参信号 → **必被走过场勾满（softness 必失控）**。

**处方方向**：让判据锚在**模型难自伪的外部入参事实**上（"ASR 出现≥2 处重复""全程无音频且无字幕"），而非主观程度词。

**规则下沉示例**：

没有形成 需求 → 任务 → 规则 的稳定转换能力，过去常常把需求或任务目标直接写成 prompt 要求，没有继续下沉成具体、可判断、可执行规则。模型仍需自行解释要求，导致执行不稳定。

示例：跨行 bbox 问题

- **需求**：严禁跨行 bbox
- **任务**：当目标内容跨行时，判断应保留哪一行作为 target 并定位
- **规则（需要进一步下沉）**：
  - 若目标内容跨两行，不要为两行共同生成一个 bbox
  - 只能选择其中一行作为 target 和 bbox
  - 优先选择信息更完整、与解题更直接相关的一行
  - 若两行信息接近，优先保留上行

#### Bad Case分析三步法

**第一步：记录并分类错误现象**

只描述"错在哪里"，不直接解释原因。例如：

- target 选对了，bbox 落错行
- 明明禁止标选项，却仍然标了 A/B/C/D
- 改了跨行策略，动作类型也一起漂移

**第二步：按失败类型归档**

| 失败类型            | 描述           |
| --------------- | ------------ |
| 识别边界问题          | 目标识别错误或遗漏    |
| 分类或 action 映射问题 | 类型判断错误       |
| 跨行与定位问题         | bbox 跨行或定位不准 |
| bbox 精度问题       | 坐标偏差过大       |
| 输出格式问题          | JSON 结构或字段错误 |
| 调试报告与实际行为不一致问题  | 日志与结果矛盾      |

**第三步：列出 2-3 个可能原因**

把可能原因映射回 ABC 三层诊断框架，形成假设，而不是直接下结论。

---

#### 数据分析地基（有一批测试数据/GT 时必做，不止看零散 badcase）

> 当测试数据不是零散几条、而是一个带 GT 的评测集时，bad case 分析要先立**数据分析地基**，再谈提示词病因。方法见 `references/data-analysis.md`（本 skill 自带一份，独立可跑）。三条铁律：

1. **从整体到具体**：先出**带符号混淆矩阵**（GT×Pred，每条错判标 偏低/偏高 × 跨一档/逆序）定主病方向，再下钻 case。分布相似但一致率低=判定标准与人不一致；分布不相似=提示词整体偏严/偏宽。
2. **收集判定证据（COT）**：不只看 level 对错，要读模型 COT/think 段"凭什么这么判"——根因藏在这里。全量看（判对的 case 凭什么判对也是信息）。多模型分别归因，不合并。
3. **返回率预判**：每条策略预判会不会把原本判对的 case 改错。

#### 分桶诊断（把现象结构化到提示词各模块）

> 这是本 skill 从"零散 badcase 归档"升级到"结构化模块诊断"的关键。完整方法见 `references/diagnosis-method.md` 切面四。

- **桶 =（提示词决策链上一个模块）↔（该模块负责的 case 子集）** 绑定对。改的单位是模块，验的证据是对应 case 桶。
- **切桶依据 = 提示词 COT/决策顺序 × 数据集 GT 分布**综合（不写死桶名）——分桶顺序贴合提示词的决策顺序（如"先判不适用→再判低→再中/高"），保证归因对得上模型的实际决策路径。
- 每桶给**准确数 + 返回去向**（判错去哪档、逆序 or 邻档）；桶内按两版落点做 **COT 落点分组**（迭代版独有误伤 / 逆序 / 两版都对的正样本锚 / 两版共错的硬骨头），逐组读 COT 定位是 prompt 哪条规则致伤。
- 按**收益大小 × 不伤已有强项**排各桶优先级，定先改哪个；每桶配独立止损线。

#### 简洁性诊断（跨版本对比）

有多个历史版本时，把它们排在一起**逐规则 diff**，数每模块规则条数怎么涨——重点抓 **CASE_PATCH 导致的规则膨胀**（每轮为救几条 badcase 加"X 即判 Y"窄规则、只增不减 = rule dilution）。判据：一条规则删掉会不会更短且不丢覆盖？会 → 冗余补丁，处方是 REMOVE/上抽，不是继续加。

#### 统一实验决策表

| 类别             | 典型现象                  | 优先怀疑                    | 优先试验                | 试验目的                                |
| -------------- | --------------------- | ----------------------- | ------------------- | ----------------------------------- |
| **A 任务定义层**    | 要求含糊、抽象、多义；标准不清；优先级不明 | 任务目标或判断标准没讲清楚           | **最小对照实验**          | 只改一条定义、标准或优先级表达，看局部是否改善             |
| **B 任务拆分层**    | 改一个局部，整体都飘；一步塞太多内容    | 任务耦合过重、流程没拆开            | **任务剥离实验**          | 删减附加任务，看核心任务是否恢复稳定                  |
| **C 规则下沉层（1）** | 模型常常"理解对了但输出不稳"       | 高层要求已理解，但执行规则不够具体       | **任务剥离实验 + 中间结果观测** | 先看模型中间判断是否稳定，再判断是不是规则没有下沉好          |
| **C 规则下沉层（2）** | 某一条规则看起来没生效           | 某条具体规则本身无效、过抽象或缺少优先顺序   | **最小对照实验**          | 只改这一条规则，验证它是否真的起作用                  |
| **D 模型边界**     | 同类 case 一直不稳，怎么改都差    | 可能是模型边界，也可能是 prompt 仍过重 | **任务剥离实验优先**        | 先排除是不是 prompt 太复杂；若最核心任务仍不稳，再考虑模型边界 |

#### 实验设计方式

**最小对照实验**：

- 只改一个局部变量
- 适合验证某条规则、某个字段、某个优先级是否真的起作用
- 目标是建立"改动—结果"最短因果链

**任务剥离实验**：

- 删掉附加负担，观察核心任务是否恢复稳定
- 适合判断问题是 Prompt 太重，还是模型本身对核心任务就不稳

**中间结果观测**：

- 要求模型输出中间判断或自评报告
- 帮助区分识别、定位、执行规则哪一层出了问题
- 适合那些"看起来都对，但最后结果不对"的场景

**停止实验**：

- 当模式已经明显时，及时停止，不要把整套测试跑完再回头解释
- 实时渲染和中途停测不是打断流程，而是诊断流程的一部分

#### 回归分析（若新旧版都有跑测结果，跑完必做）

> 当本 skill 是在"改了没效果/漂移"场景里、且拿得到新旧两版的跑测结果时，测试建议要包含一步**回归分析**——它比"总一致率涨没涨"深一层，专抓一个总分掩盖不了、逐 case 迁移也抓不全的东西：**沉默丢失**。

回归分析 = **prompt diff + 数据反馈 + COT 读取** 全流程：

1. **prompt diff（规则级）**：新旧版**逐规则 diff**，列出所有"**消失的旧规定**"与新增规定——看判据/约束条目的增删，不是措辞变化。
2. **数据反馈对照**：每条"消失的旧规定"对到"基线对→迭代错"的返回 case——这条规定消失是不是正是某些 case 变错的原因？有数据佐证 → 确认误伤元凶。
3. **COT 定位 + 抓沉默丢失**：读迭代版 COT 确认致伤规则；**有些"消失的旧规定"当前测试集里恰好没有对应 case、数据毫发无伤——这就是沉默丢失**：一条曾有效的正面约束被无意删掉，换批数据就崩。逐条判**有意删除**（策略要求，OK）还是**无意丢失**（手滑漏的，标红找回）。

**用途**：即便新版数据更好，发现"有价值旧规定被无意丢失"就要提醒用户——先找回该规定或论证它确实该删，别让它成为定时炸弹。这是"改了没效果/在松↔严振荡不自知"的解药。

## 不要做什么

- 不要按单个 case 持续堆补丁
- 不要同时修改 Prompt、测试集、渲染逻辑和输出 schema，却不记录变量
- 不要在证据不足时给出过深的根因解释
- 不要把"模型不稳定"当成默认答案，先做分层归因
- 不要在模式已经明显时继续硬跑完整轮测试
- 不要编造或联想用户未提供的信息
- 不要在有一批带 GT 的测试数据时，跳过数据分析地基（混淆矩阵+COT）直接扎进零散 badcase
- 不要把"桶"写死成固定档位清单——每次结合提示词决策顺序与数据 GT 分布现场切桶
