# 提示词诊断:从数据现象反查提示词病因

> **定位**:本文件是"提示词层-病因"。它的**输入 = `data-analysis.md` 的产物**(带符号混淆矩阵 + diff 存档 + 各 case 的 COT 片段)。data-analysis 回答"哪档偏了、哪些 case 错了、错向哪"(现象);本文件回答"**这是提示词哪个模块 / 哪一层造成的**"(病因)。现象不等于病因——"usefulness 中→高 11 条"是现象,"提示词第 N 段哪句判据把它判高"才是能落成改动的病因。
>
> 不重复讲怎么算混淆矩阵(那在 data-analysis)。本文件只讲:拿到现象后,用四个切面把它归到提示词的具体模块。

## 四个诊断切面

现象→病因的归因,从四个切面同时看。前三个定位"病在哪、病多深",第四个(分桶)是把前三个**结构化**地落到提示词各模块上的组织方式。

1. **ABC 三层结构**——病在任务定义(A)/ 任务拆分(B)/ 规则下沉(C)哪一层。
2. **入参咬合**(并入 C 层)——站在模型视角,它实际收到的入参撑不撑得起提示词要它做的判定。
3. **简洁性(跨版本)**——提示词是否因不断打补丁而规则膨胀,越改越重。
4. **分桶归因**(核心组织方式)——按提示词的**决策顺序**把现象拆到各模块,每个模块单独追踪、单独改、单独验。

---

## 切面一:ABC 三层结构检验

业务目标 → 收敛成可执行系统 → 展开成验收机制。三层各管一段,错在哪层决定了该怎么改。

| 层级 | 管什么 | 典型病象 | 错误归因 |
|---|---|---|---|
| **A 任务定义层** | 目标 / 好坏标准 / 失败定义 / 优先级 | 要求含糊、抽象、多义;标准不清;优先级冲突 | 目标不清、标准模糊、优先级冲突 |
| **B 任务拆分层** | 子任务拆分、要不要分阶段、输入输出边界 | 改一个局部整体都飘;一步塞太多 | 任务耦合、局部修改引发全局漂移 |
| **C 规则下沉层** | 把需求下沉成可判断、可排序、可执行的规则 | "理解对了但输出不稳";某条规则看起来没生效 | 规则没下沉、缺优先级、**规则要的入参不存在**(见切面二) |

**A 层检验**:模型最终产出什么(输出形式/字段/格式明确否)?什么算对什么算错(有具体判定条件,非"效果好")?哪些情况可接受失败?冲突时优先保什么?

**B 层检验**:上游能提供什么输入、哪些可用哪些不可用(输入边界)?下游需要哪些字段(区分生产/调试)?该单 prompt 还是拆多阶段?
> 项目血泪:"多维度同改必崩、崩点恒在 readable"就是典型 B 层病——单 prompt 内多类判定耦合,改任一处下压力被放大传导。解法是**分阶段双判 / 物理隔离**,不是继续在一段里调。

**C 层检验**:哪些是处理对象、哪些排除(边界)?有哪些红线(禁止项)?规则是否可执行(有具体描述,非"要准确")?规则间有优先级吗?

**规则下沉示例**(需求→任务→规则的稳定转换):
- 需求:严禁跨行 bbox
- 任务:目标跨行时判断保留哪一行
- 规则(下沉后):跨两行不共用一个 bbox / 只选一行作 target / 优先信息更完整的一行 / 两行接近时保上行

没形成这套转换能力,就会把需求或任务目标**直接写成 prompt 要求**,模型仍需自行解释,执行不稳。

## 切面二:入参咬合(并入 C 层)

> **为什么并进 C 层**:一条规则"可执行"的前提,是模型能**依据提示词对它实际收到的入参做处理**。规则要的证据入参里根本没有 → 这条规则再清晰也执行不了,病根在 C 层。所以入参咬合不是独立一层,是 C 层"规则可执行性"的深化。

诊断动作(**站在模型的角度,不是站在你的角度**):

1. **先看模型实际拿到什么入参**——不是你以为它有什么,是它真正收到的:标题、ASR/字幕文本、视频画面、检索片段、结构化字段……逐一列出。
2. **再看提示词的每条判据要什么证据**——把 prompt 里"判高/判低/判不适用"的每条触发条件,问一句:它要的证据,**入参里有没有、够不够、可不可核验**?
3. **对不上的地方就是病灶**:
   - 判据要的证据入参根本没有(如"看开篇字幕是否点题",但入参只有 ASR、没有画面帧)→ 规则悬空,模型只能瞎猜或走过场。
   - 入参有脏/空/噪声(ASR 错乱、字段为空)却被判据当可信证据用 → 模型被带偏。
   - 判据是纯主观自评("是否高效/是否卓越")、不落在任何可核验入参信号上 → **必被走过场勾满**(项目铁律:softness 必失控)。

**入参咬合的处方方向**:让判据锚在**模型难自伪的外部入参事实**上(如"ASR 出现≥2 处重复""全程无音频且无字幕"),而不是主观程度词。这与 prompt-modification 的"可外部核验硬判据"是同一条防线。

## 切面三:简洁性(跨版本对比)

> **不是**孤立看某一版 prompt 啰不啰嗦,而是**把多个版本排在一起看规则条数怎么变的**。

诊断动作:

1. 把当前版与前几版 prompt **逐规则 diff**,数每个模块的规则条数随版本怎么涨。
2. **重点抓 CASE_PATCH 导致的规则膨胀**——每轮为救几条 badcase 加一条"X 即判 Y"窄规则,条数只增不减,就是 **rule dilution(规则稀释)**:规则越多越互相干扰,模型判定越不稳,而且新窄规则往往误伤原本判对的同型 case。
3. 判据:一条规则**删掉会不会让 prompt 更短且不丢覆盖**?会 → 它是冗余补丁,本就不该在(MDL/Occam:规则要"自付其费",压掉的错误得大于它增的长度)。

**简洁性病象与处方**:版本越迭代越重、指标却不涨甚至倒退 → 多半是补丁堆积。处方是 **REMOVE / 上抽**(删窄规则或抽象成高层原则),不是继续加。这直接喂给 prompt-modification 的"加/删/改分流:过具体补丁型→删上抽"。

## 切面四:分桶诊断(核心组织方式)

> 这是本文件最重要的一节。分桶**不是瓶颈期才用的补救,而是每一轮诊断的默认组织方式**——无论大迭代小迭代,结构化都比"糊成一团全量看"更能归因。前三个切面(ABC / 入参 / 简洁性)都在"桶"这个粒度上做,才不会东一榔头西一棒。

### 什么是桶:提示词模块 ↔ case 子集的绑定对

一个桶 = **(提示词决策链上的一个环节/模块) ↔ (该模块负责判定的那批 case 子集)** 的绑定对。

- **改的单位是模块**——一次只动提示词的一个决策环节。
- **验的证据是对应 case 桶**——只看这个模块负责的那批 case 的迁移,其余模块和 case 冻结当对照。

### 怎么切桶(通用规程,不写死桶数/桶名)

> **铁律:桶不是固定的"不适用/低/中/高"清单**——那是某个项目的具体形态。切桶要**每次到现场,结合提示词与数据集 GT 综合分析**得出。

切桶依据 = **提示词的 COT / 决策顺序 × 数据集 GT 的分布**,两者综合:

- **纵切提示词(决策顺序)**:读这条提示词的 COT 是怎么一步步判的——先判什么、再判什么。每个决策环节就是一个候选模块。**分桶顺序要贴合提示词的决策顺序**(如"先判不适用→再判低→再判中/高",桶就顺着这条链切,保证归因对得上模型的实际决策路径)。
- **横切数据(GT 分布)**:看数据集 GT 落在哪些类别/档位,每类对应哪个决策环节负责判定。
- **对齐**:决策环节与 GT 类别往往天然对应(判不适用的环节 ↔ GT=不适用的 case;判低的环节 ↔ GT=低的 case)。把它们配成绑定对。**先做 GT 分布 sanity check**:某桶样本极少则该桶实质是二分类,一致率别外推。

### 每桶产出:准确数 + 返回去向

不是只报一个桶内一致率数字,而是每桶给 **准确数 + 返回去向**(判错的 case 去了哪档,带方向标签:**逆序**跨两档 / **邻档**跨一档)。这是 data-analysis 的带符号混淆矩阵**下沉到桶粒度**——桶内也要看"错向哪、错多重",而不只是"错了几条"。逆序比邻档更伤分,优先治逆序。

### 桶内 COT 落点分组

对一个桶,把它的 case 按"两版(基线 vs 迭代版)各自落点"分组,逐组读 COT 定位病灶。典型分四组(**分组数/含义按项目调,这是范式不是死格式**):

| 组 | 含义 | 诊断用途 |
|---|---|---|
| 迭代版独有误伤 | 基线对、迭代版错 | 读迭代版 COT,定位是**哪条新增/改动的规则**把它判错的 |
| 逆序错 | 判成跨两档(0 分) | 最伤分,优先;看卡在哪个决策步 |
| 两版都对(正样本锚) | 两版都判对 | 改判据时的**回归锚**:改完这组必须仍全对,否则连正样本都误伤了 |
| 两版共错(硬骨头) | 两版都错 | 提示词单点改救不动,多半是 GT 口径分歧或模型能力边界,**别当迭代目标**、交 GT 复核 |

> 这四组正是"逐 case 迁移四类"(见 data-analysis)在**单个桶内 + 读 COT 定位规则**的落地。范式实证见样板文件的"高桶 COT 落点四分组 A/B/C/D"。

### 优先级路线:先改哪个桶

把各桶按 **收益大小 × 不伤已有强项** 排序,定迭代顺序:

- 优先动**净收益空间最大、且几乎不伤其他桶**的桶(如某桶一致率极低、天花板远未触及,又相对独立)。
- **护城河桶(已很高)不主动改**,只随联动监控——任何放松动作都可能先冲垮它。
- 排序要显式写出来,不要凭感觉挑一个桶就动手。

### 每桶独立止损线

每个桶配自己的止损线(如"某桶 X→Y 逆序 >N 条即回退该桶改动")。这样跨桶泄漏一发生就能定位到是哪个桶的改动越界了,而不是笼统看总指标。

### 瓶颈时:并行分桶迭代

当串行一版一版试遇到瓶颈(净 Δ≤0 / 某桶反复横跳 / 精确抵消),**升级成并行多版**:同一轮起 V(N+1)-a / -b / -c,**每版只改一个不同模块**(或对同一模块的不同改法),并行跑测,快速比出哪个模块的哪种改法有效。判定走两阶段:

1. **桶内初筛(快)**:每版先在**自己那个桶的 case 子集**上跑,看该模块改法在自己桶上有没有效(修正率),快速淘汰无效改法。
2. **全集确认(防泄漏)**:初筛胜出的版本再跑**全量验收集**,看**返回率 / 止损线**——有没有把邻桶带崩。**只有过了全集确认(无跨桶泄漏)才能进 baseline**。

> 为什么必须两阶段:分桶改先分桶跑省时省钱,但项目最致命的病是**跨桶/跨维泄漏**(改一段却让邻段漂移)。桶内看着涨了,不代表没把别的桶带崩——所以进 baseline 前必须全集看返回率。这与 auto-eval 主循环的止损线、Part4 返回率是同一道防线。

## 诊断产出:喂给谁

本文件的诊断结论(病在哪层/哪模块、入参哪里不咬合、哪些规则该删、各桶优先级)直接喂给 **prompt-modification** 的"加/删/改分流"和"闸门一策略卡":

- ABC 定位 + 分桶 → 策略卡的"根因"字段。
- 入参咬合病灶 → 处方方向(锚可核验入参事实)。
- 简洁性/规则膨胀 → "过具体补丁型→删上抽"分流。
- 桶内 COT 分组 → 每条策略的"返回率预判"(正样本锚组会不会被误伤)。
