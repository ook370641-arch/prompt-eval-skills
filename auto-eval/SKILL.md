# 评测驱动的提示词迭代全链路引擎

## 这个 skill 是什么

它把**提示词迭代的整条链路**——读背景→数据分析→生成提示词→跑测→报告,且反复循环——固化为一套可复用的自动化编排。你的任务就是按这套流程自主跑完整条链路。

**核心理念**:本 skill 只持有**通用流程骨架和方法论铁律**,不持有任何具体项目的工作流。具体怎么跑测、数据长什么样、读哪个文件的哪个字段——这些都**写在项目的 README/CLAUDE 里,由你启动时去读;没有就由你依据当前文件夹的上下文自己创建**。skill 通用,项目细节落地在文档,二者解耦。

**你的角色**:迭代循环的**编排者** + 项目背景的**读写者** + 数据分析地基的**亲自施工者**。三个子 skill(prompt-diagnosis / prompt-creation / report-review)是你在特定环节调用的专家,但串起全链、守住铁律、打好分析地基是你不可外包的职责。

---

## 项目文档:spec、plan 与档案

本 skill 强依赖项目根目录的两份文档 + 一层历史档案。前两份的关系类似 **spec 与 plan**:

| 文档 | 角色 | 装什么 | 变化频率 |
|---|---|---|---|
| **CLAUDE.md** | spec(为什么/做什么/红线) | 完整项目背景、目标、当前任务、方法论铁律、文件目录体系 | 慢(任务级) |
| **README.md** | plan(怎么做) | api 调用方法、脚本位置与接口、数据格式与字段、缓存、踩坑、评估集结构、可复用跑测 pipeline | 较慢(工程级) |
| **档案层**(如 `docs/`) | 项目的大脑 | 全部历代迭代报告、策略文档、失败复盘、评分标准、核对看板 | 每轮追加 |

> **档案层必须按"版本 + 迭代方向"分目录,不许平铺。** Agent 是靠目录结构决定读什么的——平铺目录等于让它盲读几十个文件。CLAUDE 的「文件目录体系」章节要写清每个目录装什么,新一轮产物一律归到对应版本目录下,**只追加不覆盖**(失败版本也留,复盘价值最高)。

**一条铁律拆两面写**:同一条方法论原则,把"为什么重要 / 不可逾越的红线"沉淀进 **CLAUDE**,把"具体读哪个文件的哪个字段、怎么操作"沉淀进 **README**,不重复、各取一面。判据:换个工程实现就会变的操作细节→README;换实现也不变的任务目标/红线→CLAUDE。

例:"必须读模型推理证据(COT)再归因"这条——"读模型的判定证据是分析的红线"进 CLAUDE,"读 `运行与评测/推理结果_*.jsonl` 的 `think` 字段"进 README。

## 启动:先读上下文,再就盲区与用户对齐

**这是本 skill 的第一动作,不可跳过。** 但对齐不是"无论大小都问用户"——而是**你先自己搜集足够上下文,只把搞不清的拿去和用户对齐**。默认当前文件夹里已经藏着大部分答案。

0. **先收下用户调用时附带的描述/参数**:它是本轮的**权威任务要求**(目标维度、用户的核心洞察、特殊约束等都从这里来)。先读它,再读项目背景;Part0 必须把它落进 CLAUDE(本轮任务/目标/核心洞察/特殊约束)和 README。别把它当闲聊背景——下一轮 session 只认文档,丢了就找不回。
1. **再读项目背景,自己搜集上下文**:读项目根目录的 CLAUDE.md 和 README.md(若存在)。它们承载了这个项目"怎么跑测、数据长什么样、铁律是什么"的全部具体知识。再扫一眼项目里过往的迭代产物(历史提示词版本、评测结果、策略/报告文档),理解这个项目当前进行到哪。**基线版本从 CLAUDE 的「当前生产版本」字段读——它就是上一轮迭代的产物,读不到就列入盲区去 grill。** 能从项目文件/脚本读出答案的,先去读,不要凭空问。
2. **若两份文档不存在或不完整**:说明这是新项目或首轮。此时你要靠盘问问出足够建起这两份文档的信息(见下方"展开/改写文档"),盲区更多、要对齐的也更多。
3. **整理出一份"工作清单",只列你不清楚的,再用 grill-me 方式和用户对齐**:基于已读到的上下文,列出本轮迭代你**还搞不清、需要用户拍板**的点(每个都附你的推荐答案)。已经能从文件里读出答案的,直接在清单里写明你的判断、不必再问。然后**按 grill-me 的盘问纪律逐个 branch 对齐**(纪律很轻,直接照做,不必调用外部 skill):
   - **一次只问一个问题**,沿设计树逐个 branch 推进、按依赖顺序解决(先定目标,再定验收口径,再定尺子……),不要一次性把清单全甩给用户。
   - **每个问题都附你的推荐答案**,用户只需确认或纠偏,不是从零回答。
   - **能从文件/脚本查到的,去查,不要问用户**——盘问只针对真盲区。
   - **问到双方对齐为止**,不满足于表面点头;每个 branch 拍板了再进下一个。
   - 完整 branch 清单见 `references/grill-checklist.md`,通常覆盖:
     - 本轮要改哪个/哪些维度或指标?当前基线版本是谁?
     - 验收集是哪个?口径(总样本/有效样本/剔除规则)是什么?GT 来源与可信度?
     - 评测尺子是什么(一致率/均分/逆序率/其他)?什么叫"通过/净收益"?
     - 跑测怎么跑(对接哪个脚本、Pro/Mini 还是单模型、产物落哪)?
     - 硬止损线是什么(哪个维度退化多少条就回退)?
     - 有没有"不拟合"的 GT 排除项(人工标错的标签)?
4. **对齐结束**:把对齐结果回写进 CLAUDE(本轮任务/止损线/排除项)和 README(若发现新工程细节)。

**对齐时先判「这个任务该不该用本 skill」——命中以下任一条就直说不该用,别硬跑**:

- **输出不可自动判定**(开放对话、创意文案这类没有可判定尺子的)→ 闭环从根上不成立,先解决"拿什么当尺子",或转人工评估。
- **只打算迭代一两轮**(一次性任务、临时活动)→ 触顶前的头两版靠蛮力就能拿下,三道闸门是纯开销;可解释性的价值要到第三轮以后才开始回本。
- **单轮跑测成本极低**(秒级、免费)→ 暴力试错比走闸门更快,本 skill 的纪律是为"一轮数小时 + 真金白银"的场景设计的。

> 另有三条**"能用但该停手"**的条件(近天花板 / GT 不可信 / 某档样本极稀疏),它们要等 Part1 分析出数据才能判,见 Part1 末尾「何时停手」。上面三条是**开工前**就能判的,判出来直接告诉用户。

> 为什么先读上下文再对齐:提示词迭代最大的浪费是"基于错误的目标理解跑完一整轮(数小时 + 真实 API 成本)才发现方向错了"。但反过来,把项目文件里已有的答案也拿去问用户,是另一种浪费。正确姿势是**先吃满上下文、只对真盲区做一次集中对齐**(grill-me 方式:一次一问、附推荐答案、能查不问)。完整 branch 清单见 `references/grill-checklist.md`。

## 主循环:Part0→1→2→3→4,按需循环

工作顺序**不是** 0→1→2→3→4 走一遍就结束,而是 **0,1,2,3,4,1,2,3,4,...** 的循环——起码跑两轮(一轮基线、一轮迭代版),按评测结果动态决定迭代几轮、生成几版提示词。

> **每一 Part 都有"验收物"——一个落在固定路径的产物文件,不产出即视为该 Part 未完成。** 路径由项目目录约定决定(写在 README 的"文件产出清单"里),skill 只规定"必须有验收物 + 必须落在 README 约定的位置"。下面每个 Part 末尾的「✅ 验收」即此意。

> **分桶是贯穿主循环的默认组织方式(不是瓶颈期才用的补救)。** 无论大迭代小迭代,Part1 分析、Part2 改、Part3 测、Part4 归因都沿"**桶 =(提示词决策链上的一个模块)↔(该模块负责的 case 子集)**"的绑定对来结构化组织——改的单位是模块、验的证据是对应 case 桶,其余模块冻结当对照。**一轮可以改多处,但每处改动必须可独立归因——必须让多处改动落在互不重叠的桶上,禁止同一个桶内一轮动两处**(效果落在同一批 case 上,事后无法分账);**改动数量本身不设上限**。违反则该轮视为不可归因,指标涨了也不得晋升 baseline。桶怎么切(按提示词 COT 决策顺序 × 数据集 GT 分布综合、不写死桶名)见 `references/diagnosis-method.md` 切面四。**遇到瓶颈时(全量净 Δ≤0 / 某桶反复横跳 / 修对 N 条同时误伤 N 条精确抵消),推荐从串行升级为并行分桶迭代**:同轮起多个 V(N+1)、每版只改一个模块,判定走"**桶内初筛(修正率)→ 全集确认(返回率/止损线)才进 baseline**"两阶段(详见 diagnosis-method 切面四「瓶颈时」)。

### Part 0 — 展开/改写项目文档(地基的地基)

把 grill-me 盘出的信息,落成/更新 CLAUDE(spec)和 README(plan)。**没有则新建,有则改写**。这是后续所有工作的上下文锚点,也保证下一个 session 能接上。

**✅ 验收**:项目根目录有 CLAUDE.md(spec)+ README.md(plan)两份,且**用户调用时附带的任务要求(目标/核心洞察/特殊约束)已写进 CLAUDE 的「本轮任务」**,止损线/GT 排除项已写进 CLAUDE,本轮工程细节已写进 README;**档案层目录已按"版本+迭代方向"建好,并在 CLAUDE 的「文件目录体系」里登记**。

### Part 1 — 数据分析(整条链的地基,你亲自施工)

**这一环本 skill 自己做,不外包给子 skill。** 它是最重、最值钱、也最容易被偷懒跳过的一环。三条**通用方法论铁律**(写进 skill 是因为它们跨任务通用,不是写死工作流):

1. **从整体到具体**:先看整体数据偏移(分布、混淆矩阵、一致率方向),定位"主病往哪偏",再下钻到具体不一致 case(diff case)找根因。不要一上来就扎进单个 case。
   - **下钻的前提是带符号的混淆矩阵**:整体那一步的产出不是一个一致率数字,而是 `GT×Pred` 混淆矩阵 + 每条错判的**方向与严重度**(偏低/偏高 × 跨一档/逆序)。没有这张带符号的矩阵,"主病往哪偏"就无从谈起,case 下钻也没有依据。
   - **先读分布相似度,再定病性**:把模型判定的档位分布与 GT 分布并排看——
     - 分布**相似但逐 case 一致率低** → 多半是**判定标准与人不一致**(错判东边错一个西边错一个、相互抵消了整体分布),整体统计看不出病灶,**必须对具体不一致 case 做更细的逐 case 分析**才能挖根因。
     - 分布**明显不相似**(模型整体偏向某档) → 提示词**整体偏严或偏宽**,先从"哪一档被系统性高估/低估"入手。
2. **必须收集归因所需的全部辅助证据**:不能只看"输入→输出 level 对不对"就归因。**必须收集模型"凭什么这么判"的证据**——带推理链的模型就是 COT/think 段(根因藏在这里,不读就只能猜);其他形态可能是中间打分、检索片段、置信度。**全量分析**(不只看 badcase,要看全部 case,因为"原本判对的 case 模型凭什么判对"同样是信息)。
   - **多模型须分别归因**:若本轮涉及多个模型(如 Pro/Mini),不能把它们的错判合并看。**同一条提示词在不同模型上偏置方向可能相反**——必须分模型各看一套混淆矩阵、各找各的 case 规律,因为 prompt 是"针对某模型偏置的纠偏器",给 A 模型的处方套到偏置方向不同的 B 模型上会过纠(详见关键原则速查「prompt=纠偏器」)。
3. **返回率预判**:得出策略后,**必须预判这条新策略会不会把原本判对的 case 改错**(误伤)。只治病不顾误伤,就会犯"证明局部有效却没证明值得采用"的错。这是**写前预判**,跑测后由 Part4 的「返回率实测 + 归因」闭环检验。
   - **迭代未见收效 = 上一轮分析有漏,必须更深一轮再分析,而非急着再改提示词**。最常见的漏就是没做返回率预判——只盯着治某批病,没看到新策略在原本判对 case 上的误伤,净 Δ 被抵消。"改了没动静"是数据分析不够深的信号,回到本 Part 重挖,不要靠多生成几版提示词去撞。

> 这三条的"为什么"进 CLAUDE 当铁律,"在本项目具体读哪个文件哪个字段、怎么算混淆矩阵"进 README 当操作指南。数据分析(数据层-现象)的可复用细节见 `references/data-analysis.md`;拿到数据现象后,怎么反查"这是提示词哪个模块/哪一层造成的"(提示词层-病因,含 ABC 三层 + 入参咬合 + 简洁性 + 分桶归因)见 `references/diagnosis-method.md`。**分析产物出来后必接一步诊断**(读 diagnosis-method),不是可选动作——Part1 的地基是"现象 + 病因"两层,只有现象没有病因,Part2 就无从下手。

**何时停手(分析完先判这一步,禁止无脑往下改提示词)**:以下三种情况**禁止继续迭代提示词**,必须改做别的事,并在报告与 CLAUDE 里写明停手理由——

- **该维度已近天花板**(实测 86%~91% 量级)→ 任何改动都落入"原 badcase 纹丝未动 + 新增漂移",负 ROI。**停手**,把预算移到低分维度。
- **GT 本身不可信**(某维度改标率 >5~10%)→ 这是评分标准的系统性问题,不是提示词问题。**停手**,推动重标该维度 / 修订评分标准。
- **某档样本极端稀疏**(如某档仅 1 条,该维度实为二分类)→ 一致率不可外推,改了也证不出。**停手**,先提评测集扩容需求。

**产出**:一份数据分析文档,说清每个维度的偏差方向、根因(带 COT 证据)、提示词策略、以及每条策略的返回率预判风险。这份产出要能直接喂给 Part 2(且每条策略要在 Part2 闸门①出示给人工批准)。

> **分析产物出来后,必接一步「提示词诊断」——不可跳过。** 数据分析(data-analysis)只给"现象"(哪档偏、哪些 case 错、错向哪、COT 怎么想);把现象反查成"提示词哪个模块/哪一层的病"(病因)要读 `references/diagnosis-method.md` 做:ABC 三层(C 层看**入参咬合**)+ 跨版本**简洁性**(查规则膨胀)+ **分桶归因**(按 COT 决策顺序把现象拆到各模块、每桶给准确数+返回去向、桶内 COT 落点分组、定优先级)。**只有现象没有病因,Part2 无从下手、只能瞎改。** 这一步的病因结论直接喂 Part2 的加/删/改分流与闸门①策略卡。

**✅ 验收**:两件,缺一即 Part1 未完成——
1. **机器生成的结构化分析产物**(客观背书,不可手写注水):一个脚本跑出来的 ① **逐不一致 case 存档(diff case)**(每条带 GT / 模型判定 level / 是否一致 / 该 case 的 COT 片段)+ ② **整体分布与带符号混淆矩阵**(GT 与模型各档高/中/低的分布率、`GT×Pred` 矩阵、各不一致类型条数)。这是"整体→具体"和"读 COT 归因"两条铁律的落地产物,不是额外动作。落在 README 约定位置(本项目为 `Prompts/V{N}数据分析/`,脚本 + 不一致 case jsonl + 分布表)。
2. **数据分析/策略文档**:由上面那份机器产物背书,含每维度的混淆矩阵/偏差方向、带 COT 的根因、策略、返回率预判风险。**且必须含「提示词诊断」段**(读 `diagnosis-method.md` 产出):现象→病因的归因——病在 ABC 哪层、入参哪里不咬合、跨版本简洁性/规则膨胀、**分桶结论**(各桶准确数+返回去向、桶内 COT 落点分组、桶优先级路线)。落在 README 约定的 docs 位置(本项目为 `docs/{版本}提示词策略.md`)。

> 为什么要机器产物闸门:策略文档是叙述性的、可以注水——agent"心算一下分布、扫几条 case"就能声称做了整体分析。把分布/矩阵/不一致 case 存档固化成脚本产物,"分析做没做、做到什么深度"就从"看文档写得好不好"变成"看产物在不在、分布对不对得上",验收抓得住。

**可选辅助验收物——人工核对看板(xlsx/html)**:当某维度需要人逐 case 复核 GT 与模型判定(尤其样本有系统盲区、或 GT 本身要校验时),产出一份一行一 case 的核对表:GT / 各模型判定·分数·偏差 / 各模型的判定证据(COT 片段) / 人工备注栏。**模板与列结构、产出路径写在 README/CLAUDE,不写进 skill**(每个项目的列、维度、COT 抽法都不同)。本项目示例:`docs/{版本}/{维度}核对看板.{xlsx,html}` + 生成脚本 `gen_*_dashboard.py`,列结构见 README「人工核对看板」节。

### Part 2 — 提示词迭代(效果层→措辞层 精修框架 + 闸门①②)

本环把 Part1 的策略落成新提示词。**用一套防回归的精修框架贯穿**:先 **效果层(Reflector)** 定"想要的效果"(intent),再 **措辞层(Refiner)** 落"怎么写"(wording),两段绝不合并——合并就是"边想边写",窄规则就是这么混进去的。此后本文正文一律用中文「效果层 / 措辞层」指这两段。

全链共**三道闸门:闸门① 写前审方向 / 闸门② 跑前审覆盖 / 闸门③ 晋升审沉默丢失**,三道各挡一种失效模式,不合并、不互相替代。本环设前两道:闸门① 写前人工挡方向、闸门② 跑测前机器挡覆盖,两道都过才进 Part3 跑测;闸门③ 在 Part4 §3.5(跑测后,挡沉默丢失)。

> **核心防线:数据分析结论禁止原文焊进提示词。** 分析说"X 类仍可判高",最自然的动作是加一条"X 即判高"——这几乎必然过拟合,治眼前几条却让回归率暴增(文献:rule narrowing / rule dilution)。正确做法是先抽成**与措辞无关的效果**,再落成**可复用原则**,永不嵌具体 case。完整框架(效果层→措辞层框架来源、加/删/改决策表、CASE_PATCH 拒收、GT 错前置筛)见 `references/prompt-modification.md`,**写提示词前必读**。

#### 写之前先分流:加 / 删 / 改(防回归的核心)

每条策略动手前先判属于哪一型——**先问"是加还是删",别默认加**(你的主病就是什么都往里加):

| 优先级 | 类型 | 病象 | 动作 |
|---|---|---|---|
| 1 | 遗漏型 | 提示词没覆盖该类 case | **ADD 一条原则**(描述类别,不描述个例) |
| 2 | 过具体补丁型 | 已有"X即判Y"窄规则在误伤 | **REMOVE / 上抽**(删窄规则或抽象成高层原则) |
| 3 | 过严/过宽型 | 骨架约束触发条件太松/太紧 | **EDIT 收窄/放宽触发条件,绝不删整条骨架** |
| 4 | 耦合型 | 单 prompt 内多类约束相互放大 | **REWRITE:物理隔离 / 分阶段双判**——**谨慎触发,仅在前三型都失效后才用**(它要整段重写,须在闸门①预标) |

> 优先级即尝试顺序:**能靠加原则/删窄规则/改触发条件解决的,不许直接跳到重写隔离**。第 4 型代价最高(重写让逐规则 diff 失效、闸门③ 抓不出沉默丢失),是最后手段不是首选。

并在分流前过一道**轻量前置筛**:这是 prompt 能治的,还是 GT 本身标错?GT 错走 `references/prompt-modification.md` 的四条硬证据(逆序+高置信+二模型同向+COT 客观事实)+ 盲评,真错才进 CLAUDE「GT 排除项」、不改 prompt;**证据不足一律当 prompt 问题处理**。GT 错最后再筛,别占主精力。

#### 闸门①:策略人工逐条对齐(= 效果层产物审核,写提示词前,强制)

1. 开头先报:**"我总结了 N 条策略"**,让用户知道一共要过几条。
2. 逐条出示策略卡,每条含以下各项:
   - **根因**:针对 Part1 诊断的哪条根因(如"usefulness 过松,中→高 11 条")
   - **证据**:支撑这条根因的 COT 片段 / 分布数字
   - **想要的效果(效果层产物)**:与措辞无关的效果描述(如"让模型对纯资讯罗列不再判高"),**不是**一句待焊入的规则
   - **分流类型**:加原则 / 删上抽 / 改触发条件 / 隔离(上表四型之一)
   - **验收范围**:这条策略负责哪个桶、哪批 case(事后要靠它把每条 case 的翻转落回唯一一张卡)。**多张卡的验收范围禁止重叠,同一个桶内只允许一张卡**;违反的卡必须合并成一张或拆到下一轮
   - **为什么治这根因**:这改动凭什么能治这个病
   - **返回率预判**:会误伤哪类原本判对的 case(Part1 铁律3 的产出)
   - **(仅重写时)本段重写标注**:若该策略落地需要 REWRITE-整段(非 EDIT-局部),必须在此写明「本段重写 + 为什么必须重写而非局部改」(通常是耦合型→隔离/分阶段双判,或诊断要求重写决策逻辑)。**没有这步预标,闸门②会打回任何 REWRITE hunk**。EDIT-局部型策略无需此栏。
3. **逐条批准**(可批 A、驳 B、改 C,互不阻塞);被驳的回 Part1 重挖根因或换策略,其余进下一步。

> 闸门①审的是 **效果层的效果描述 + 分流类型**——审"该不该追求这个效果、该加还是该删",**不是**审措辞。人工挡的是**方向**。下一道「提示词验证」(机器,写后,挡**覆盖**)在本环末尾。这两道的失效模式不同,不合并、不替代。

**这道闸门实际拦下来最多的不是"方向选错",而是「假归因」。两种形态**:
- **强行归因**:这条根因解释不了这批 case,只是找了个看起来沾边的规则挂上去。
- **跨维度借判据**(更危险,因为看起来最像真的):根因所用的判据属于**另一个维度**的职责。例:某维度高档被大面积压成中档,诊断链是"内容浅层 → 命中『简单≠高』排除项 → 判中",推理链原文确实这么写、覆盖面也宽;但该维度判的是**信息传递效率**,内容深浅是**另一个维度**的事——判据拿错了尺子,照它改必崩。

**动作要求:出策略卡时必须逐条自检这两种形态**,根因所依赖的判据必须属于本维度的职责范围;**跨维度借判据的策略卡一律不得提交**,退回 Part1 重挖根因。

#### 写提示词(= 措辞层,调 prompt-diagnosis + prompt-creation)

把批准后的效果描述落成实际措辞。**铁律:禁止把数据分析的 case 内容、GT 标签、单条 case 特征原文照搬进 prompt**——措辞层写可复用原则,不写 case 备忘录。

**落每条规则前过「三道验证」**(写规则时自检,闸门②再核一遍;三问依次治泛用性低 / 规则收益低 / 规则堆积):

| 验证 | 问题 | 不通过怎么办 |
|---|---|---|
| **泛用性** | 它描述的是一个**类别**,还是一条 case? | 出现具体样本名 / 单 case 特征 / GT 原文 → 判为 CASE_PATCH,**拒收**,回去抽成原则 |
| **ROI** | 它跨几条 case 复现? | 只来自 1 条 badcase → 支撑不足,先存疑不写。**≥3 条同型才够格成规则** |
| **冗余性** | 删掉它,提示词会不会更短且不丢覆盖? | 会 → 它是冗余补丁,本就不该在(**规则必须自付其费**:压掉的错误得大于它增的长度) |

> **写时纪律:默认最小手术式 in-place 改动,禁止整段重写。** 改提示词默认只对触发条件/限定词做局部增删(EDIT-局部),保留原段骨架措辞不动。**禁止把基线某段措辞整段替换或推倒重排**(REWRITE-整段)——重写会让 §3.5 回归分析的"逐规则 diff"失效(diff 全是改动 = 抓不出哪条是沉默丢失),正是"重写降低可解释性、迭代天翻地覆"的根因。唯一例外:策略分流类型是「耦合型→隔离/分阶段双判」、或 Part1 诊断明确要求"重写某段决策逻辑"时,重写是治病手段——但**必须在闸门①的策略卡里预先标注「本段重写 + 为什么必须重写而非局部改」**,闸门②见到这个预标才放行对应的 REWRITE。未预标的重写一律退回改成 EDIT-局部。

> **诊断动作必做,不可跳(强制)。** 提示词诊断——把现象反查成"提示词哪个模块/哪一层的病"——是 Part1 末尾就该完成的强制步骤(读 `references/diagnosis-method.md`:ABC + 入参咬合 + 简洁性 + 分桶)。它的结论是本环加/删/改分流和闸门①策略卡的输入。**没有诊断结论就直接改提示词 = 瞎改**,这是本 skill 明令禁止的。
>
> 在此基础上,是否**额外 invoke `prompt-diagnosis` skill** 做一遍完整 11-step 流程,是可选的(它和本 skill 各持一套 diagnosis-method,能力等价):
> - **prompt-diagnosis**(可选增强):当策略复杂、需要走完整的诊断报告→策略对齐→分轮提问流程时调用;否则直接用 diagnosis-method 的方法在本环内完成诊断即可。
> - **prompt-creation**:把批准后的效果落成实际措辞;新任务或大改时用它做任务建模。

**诊断动作(读 diagnosis-method 做归因)不可跳,哪怕只改一句**——都要说清针对哪条根因、想要什么效果、为什么这么改。**闸门①的人工批准 + 禁 case 照搬铁律同样不可跳。** 至于要不要 invoke 外部 skill 走完整流程,才是可自行判断的部分(只改一两句封顶项、策略单一时可省)。

#### 闸门②:提示词验证(写完,跑测前,派子 agent)

写完新提示词、跑测前,**派一个独立子 agent** 做映射核验——不是写提示词的自己回头看(有确认偏差,刚写完会下意识觉得都治了),而是让独立视角挑漏。

子 agent 拿 Part1 的**每条根因 + 分布问题**,到**新提示词与基线的 diff**(此处 diff 指提示词的逐行/逐规则差异,不是 GT 与模型判定不一致的 case)里做双向映射:
- 每条根因必须有**一处可指认的 diff 改动**针对它;每处 diff 改动也必须说清**针对哪条根因**。
- 产出**根因↔diff 映射表**,列三类:已覆盖(对应哪处改动)/ **漏治(无对应改动)**/ **对不准(改动找不到针对的根因)**。
- **额外查 CASE_PATCH**:diff 里有没有把具体 case 内容 / GT 原文 / 单 case 特征焊进 prompt?发现一律打回上抽成原则(这是本框架的防回归核心,不可省)。
- **查 REWRITE-整段(可解释性检查)**:给每处 diff hunk 打四类标签之一——**ADD**(纯新增条目)/ **DELETE**(纯删旧条)/ **EDIT-局部**(原有骨架措辞保留,只改触发条件或限定词)/ **REWRITE-整段**(原段措辞被整段替换/重排,原句消失)。分界看"原有那段的骨架措辞还在不在"。**凡 REWRITE-整段 hunk,必须能在闸门①的策略卡里找到对应的「本段重写+理由」预标**;找不到预标的 REWRITE 一律打回,退回改成 EDIT-局部(防"重写降可解释性、规则沉默丢失",详见上面写时纪律)。耦合型/诊断要求重写但没预标的,也先打回补标。
- 漏治、对不准、含 CASE_PATCH、或**含未预标 REWRITE** 的,回去改提示词,**不带着已知缺口跑测**——分析说了 5 个病、提示词只治了 3 个就跑测是浪费一轮(数小时 + 真实 API 成本)。

这是 Part4「逐 case 迁移核验」的**跑测前镜像**:后者看跑测后 case 怎么迁移,前者看跑测前 prompt 改动有没有对准病、有没有夹带窄规则。**无论根因几条,这道核验都必须由没参与改写的子 agent 做,不得自核**——刚写完的人回头看自己有确认偏差,会下意识觉得都治了;独立性靠角色隔离保证,不靠提醒。

#### 提示词版本管理

按项目约定的版本命名(如 V1/V2/V3),**永不覆盖,始终新版本**。注意输出格式与跑测脚本兼容(占位符、标签包裹等,具体见 README)。可按评测结果动态生成 2-3 版。

**✅ 验收**:新提示词落在 README 约定的 Prompts 位置(本项目为 `Prompts/V{N}.md`),格式与跑测脚本兼容,且已在跑测脚本的 PROMPT_MAP 注册;**闸门①:策略已逐条人工批准(每条含效果层的效果描述 + 分流类型 + 验收范围,且各卡验收范围互不重叠、同桶只一张,被驳的已回 Part1)**;**闸门②:根因↔diff 映射表已过(无漏治/对不准、无 CASE_PATCH 照搬,或漏治项已显式说明为何不改)**。

### Part 3 — 跑测(对接项目脚本,本 skill 不实现)

**本 skill 不实现跑测逻辑**(api/数据格式/视频通路每个项目都不同,写进 skill 必然带进具体工作流)。你的职责是**读懂 README 里记录的项目跑测能力,按迭代需要调用它**;**一个合格的跑测脚手架该长什么样、产物怎么组织、看板怎么设计、口径怎么锁定,见 `references/test-harness.md`**(通用方法论,不含任何项目 api/密钥/路径):

- 从 README 获知:跑测脚本在哪、怎么调、要不要先缓存、产物落哪、Pro/Mini 还是单模型。
- **起码跑两轮**:一轮基线(当前生产版),一轮迭代版,保证 A/B 对照同口径、同尺子、同运行条件。
  - **必须 temperature=0**:温度非 0 时的重跑随机性是 A/B 对照中**最致命的隐藏混杂变量**——小样本下一条 case 的"翻转"可能根本不来自你的改动,而是抖动。基线与迭代版**都必须把温度固定为 0**,跑测前先确认执行器已钉死;温度没钉死,归因表上就有假账。**仅当执行器无法固定温度时**,才退到兜底:对结论关键的少数 case,**同输入重跑 3 次取众数**再纳入对照,并在报告里标明该轮温度未固定。
  - **引入新输入信号要先验质量**:若本轮改动是给模型喂新信号(ASR、检索片段、新字段),先**人工抽检信号质量**(给出字准率/命中率),并确认信号**真的注入了**——脏/长信号比无信号更伤(模型会过度加权文本信息量而判偏),而"信号其实是空的却变好"=重跑抖动伪装的安慰剂,不是收益。
- **跨样本集的一致率绝对值不可直接比版本优劣**(样本/GT 来源不同);唯一合法的跨集对照是**同 nid 同 GT 的受控机制对照**。
- 跑测中实时监控**止损线**:某维度退化超过阈值(如 readable 中→高 >N 条)即判该维度回退。
- 若项目无跑测脚手架(新项目):提示用户"先建好跑测脚本",或引导建一个最小可跑版本,但**把它当作项目能力沉淀进 README,不写进 skill**。

**✅ 验收**:基线 + 迭代版的推理产物各一份,落在 README 约定的运行目录(本项目为 `运行与评测/V{N}/...`),Pro/Mini 按口径齐全,断点续传跑完。

### Part 4 — 评测与归因(调 report-review 自审)

> **本环是整条链路的真正终点,也是最值钱的产出。** 跑出新版提示词、拿个一致率数字不是终点——评测后的数据分析(三分类迁移 + 归因)才是。**迭代完成的数据分析比单纯迭代更重要。**

#### 1. 评测打分

用项目的评测脚本对跑测结果打分(尺子见 README)。

#### 2. 三分类迁移归因 xlsx(硬验收物,派子 agent 填备注)

别用"总一致率涨没涨"判定效果——**净 Δ≈0 常掩盖大量逐 case 翻转**(修对 N 条同时误伤 N 条,精确抵消)。把基线→迭代版的逐 case 变动落成一张 xlsx,分**三类**(去掉稳定盘"维持对"):

| 类别 | 含义 | 子 agent 填的备注 |
|---|---|---|
| ① badcase 成功矫正 | 基线错→迭代对 | 策略是否成功(为什么这条治好了) |
| ② badcase 未矫正 | 基线错→迭代错 | 策略为何仍失败 + **是否模型能力边界**(提示词治不了) |
| ③ goodcase 返回 | 基线对→迭代错 | 为何被误伤 + **哪个策略干的**(读迭代版 COT 定位:少了一条规则 / 多了一条窄规则) |

**列**:nid / url / 原始 COT(迭代版)/ GT / 现在结果(迭代)/ 原先结果(基线,对比)/ 人工备注(留空行供人填)。

**备注由派子 agent 填**(非人填):①②类判"策略成功/失败/能力边界",③类做**返回归因**(= `references/prompt-modification.md` 的效果层对返回 case 再跑一遍诊断)——**读迭代版 COT,定位是哪条新增/改动的规则致伤**,判定**少规则**(漏约束)还是**多规则**(加了窄规则/CASE_PATCH)。样本小则全量归因,大样本可采样但须 log 采样率(不静默截断)。

#### 3. 算两个指标(只算本轮改动维度)

- **修正率 = ① / (①+②)**:基线 badcase 里多少被矫正。
- **返回率(实测) = ③ / (③+维持对)**:基线 goodcase 里多少被搞坏。
- 未改维度不算返回率,作"波动监控"——不忽视(报告里报)、不强调(不套返回率),止损线照旧。

**决策用法**:**净 Δ(修正条数 − 返回条数)= 准出决策指标**(>0 才算净收益成立);**返回率 = 准出红旗**——即使净 Δ 为正,返回率过高也说明"治此伤彼、策略不稳",必须在报告标红、要求人工判"值不值得采用"(呼应 report-review「证明可行 ≠ 证明值得」)。但不自动硬回退,硬回退仍归止损线。

> 修正率/返回率的核心价值:**不让人躲在汇总净 Δ 背后**,逼你同时看"治好多少"和"搞坏多少"两个方向(和铁律「数据只看汇总会骗人」一脉相承)。

**同一套分布判据也要用来读迭代结果**(把 Part1 的"分布相似度定病性"回头套到新版上):

- 一致率上升 **且** 分布偏移改善 → 方向正确。
- 一致率上升 **但** 偏移不变甚至加剧 → **危险信号**:很可能是靠一条不合理的规则拿到了正向结果(类比:把所有黑白视频判为"深度深"——若黑白视频平均确实更深,指标会涨,但"黑白"本不该是判据)。这类规则换一批数据必崩,**必须在报告标红,并在闸门③ 判是否放行晋升**。

**单条规则的取舍模型**(把两个指标翻译成动作,逐条规则套):

| 修正率 | 返回率 | 决策 |
|---|---|---|
| 高 | 低 | **保留规则** |
| 低 | 高 | **删除规则** |
| 高 | 高 | 查该规则导致的具体矫正与返回 case,寻求更"窄"的规则表述 |
| 低 | 低 | 检查入参是否为该规则提供了足够判据,寻求更贴近入参信息、更可执行的措辞 |

#### 3.5 回归分析(三分类 xlsx 的规则级下钻 + **闸门③ 晋升 baseline 核查**,每轮跑完必做)

> **回归分析是三分类 xlsx 的同一步、更细颗粒度**:xlsx 停在 case 层(哪些 case 改对/改错),回归分析再下钻到**规则层**(是提示词的哪条规定动了导致这些迁移),并专门抓一个 xlsx 抓不到的东西——**沉默丢失**。

它是 **prompt diff + 数据反馈 + COT 读取** 的全流程,三步:

1. **prompt diff(规则级)**:把迭代版与基线 prompt **逐规则 diff**,列出所有"**消失的旧规定**"和"新增的规定"——不是看措辞变化,是看**判据/约束条目**的增删。
2. **数据反馈对照**:把每条"消失的旧规定"对到 §2 的 ③返回 case——这条规定的消失,是不是正是某些 goodcase 变错的原因?有数据佐证的 → 确认是误伤元凶(和 ③返回归因合并写)。
3. **COT 读取定位 + 抓沉默丢失**:读迭代版 COT 确认致伤规则;**关键:有些"消失的旧规定"当前验收集里恰好没有对应 case,数据毫发无伤——这就是「沉默丢失」**:一条曾经有效的正面约束在措辞层重写时被无意删掉了,是定时炸弹,换一批数据就崩。逐条判每个"消失的旧规定"是**有意删除**(策略要求的,OK)还是**无意丢失**(手滑漏的,标红)。

**⚠️ 闸门③ 晋升 baseline 核查(跑测之后,抓沉默丢失,强制)**:三道闸门的第三道,与闸门①(写前审方向,人工)、闸门②(跑前审覆盖,独立子 agent)口径一致、失效模式不同,不可合并互替。**一个新版即便数据指标更好,只要本环发现"有价值的旧正面规定被无意丢失、且未被数据佐证需要删",就不得晋升为新 baseline**——先把该规定找回、重跑确认,或明确论证它确实该删,才能晋升。这是防"每轮悄悄丢掉上轮正面约束、在松↔严一维振荡不自知"的闸门(实证:某维度连续四轮越改越差,每轮都在松↔严之间振荡)。

回归分析结论(消失的规定 / 是否数据佐证 / 有意删 or 沉默丢失 / 晋升是否放行)**回写 CLAUDE「迭代教训」累加**,与 §4 的 ③返回归因合并。

#### 4. 返回归因回写 CLAUDE(闭环)

③类的返回归因结论("策略条 #X 误伤了 Y 类 case,少/多了某规则")回写 **CLAUDE「迭代教训」累加**(现有机制,不覆盖旧教训)。下轮 Part1 直接读它,决定"收窄/改哪条策略"——这正是加/删/改决策表里"过具体补丁型→删上抽"的输入。

闭环:**Part1 返回率预判 → Part4 返回率实测 + 归因 → CLAUDE 累加 → 下轮 Part1 读它再挖**。预判错没错、哪条策略是误伤源,下轮开局门清。

#### 5. 撰写报告 + report-review 自审

报告形态固定:**评新增方案 + A/B 对照**——本轮提示词相比基线是否净收益、是否伤其他维度。把定性交代清楚,让 report-review 用现成 reference 审证据链(主问题→样本口径→判定标准→评测工具→主结果→解释边界→决策→下一步)和双轴(直观可信度/剖析深度)。**本 skill 不内置报告骨架**(避免与 report-review 重复维护、避免把报告形态写死)。报告审过后,**回写 CLAUDE**:更新当前生产版本、本轮决策、下一步;新踩坑回写 README。

**✅ 验收**:① 评测产物(逐 case 评分 jsonl);② **三分类迁移归因 xlsx**(三类 + 子 agent 备注 + 指定列,落 README 约定位置);③ 修正率/返回率已算(只算改动维度)、返回率红旗状态已标;③.5 **回归分析已做**(prompt 逐规则 diff 出"消失的旧规定" + 数据佐证对照 + 沉默丢失判定 + **闸门③ 晋升放行/拦截结论**);④ ③类返回归因 + 回归分析结论已回写 CLAUDE「迭代教训」累加;⑤ 迭代报告经 report-review 过审。各落 README 约定位置(本项目报告 `docs/{版本}报告_*.md`、评测 `运行与评测/V{N}/`、xlsx 路径见 README)。

### 循环条件

- 达标(净收益成立、无维度崩盘、过绝对准出线、**且闸门③ 放行——无有价值旧规定被沉默丢失**)→ 该版可候选生产版,冻结决策,结束循环。
- 任一维度大幅回退/触止损线 → 该维度回退至基线措辞,带着新认知回到 Part1 或 Part2 再来一轮。
- **闸门③ 发现沉默丢失** → 即便数据更好也**不晋升 baseline**,先找回该规定/论证该删,再重跑。
- 错误尝试不长期落盘,只留单文件复盘(位置见项目约定)。

## 关键原则速查

| 原则 | 说明 |
|---|---|
| skill 通用,细节进文档 | skill 不写任何具体工作流;跑测/数据/字段全在 README,任务/铁律全在 CLAUDE |
| 先吃满上下文再对齐盲区 | 用错误目标跑完一整轮是最大浪费;但把文件里已有的答案也拿去问用户是另一种浪费。先读满项目文件,只把真盲区整理成清单,用 grill-me 一次集中对齐 |
| 数据分析是地基 | 全量分析 + 读模型判定证据(COT) + 返回率预判,三条铁律不可跳;**迭代未见收效=分析有漏(多半漏了返回率预判),回 Part1 再挖,别急着多生成几版** |
| 分析后必接诊断(强制) | 数据分析只给"现象",**必接一步提示词诊断**(读 `diagnosis-method.md`)把现象反查成"提示词哪层/哪模块的病"(病因):ABC(C层看**入参咬合**)+ 跨版本**简洁性**(查规则膨胀)+ **分桶归因**。诊断动作不可跳(哪怕只改一句);是否 invoke prompt-diagnosis skill 才可选 |
| 分桶是默认组织方式 | 桶=**(提示词决策链一个模块)↔(该模块负责的 case 子集)**绑定对,改的单位是模块、验的证据是对应 case 桶。按 **COT 决策顺序 × GT 分布**切桶(不写死桶名),每桶给准确数+返回去向、桶内 COT 落点分组、优先级路线、独立止损。**瓶颈时并行多版**(每版改一模块),判定走"桶内初筛→全集确认返回率才进 baseline"两阶段 |
| 站在模型角度看入参 | 诊断 C 层要**站模型视角看它实际拿到的入参**(标题/ASR/画面),再看提示词判据要的证据入参里有没有、够不够、可不可核验;判据悬空(要的入参没有)或纯主观自评(不落任何可核验入参)必失控——锚可外部核验的入参事实 |
| 整体→具体 | 先看带符号混淆矩阵(偏低/偏高×跨档/逆序)定主病方向,再下钻 case;**分布相似但一致率低=标准不一致**(case 要求更高),**分布不相似=提示词整体偏严/偏宽** |
| prompt=纠偏器非绝对质量物 | prompt 是针对**特定模型偏置**的纠偏器;同条 prompt 在不同模型上可反向。**多模型必须分别归因、分别决策、分别止损**,不能用强模型成功外推弱模型 |
| 数据只看汇总会骗人 | 净 Δ≈0 常掩盖大量逐 case 翻转(修对 N 条≈误伤 N 条);**必须拆「维持对/维持错/改对(方向)/改错(方向)」核验迁移**;**跑测必须 temperature=0**——温度非 0 时的重跑抖动是 A/B 最致命混杂变量,仅执行器无法固定温度时才退到"关键 case 同输入重跑 3 次取众数"兜底 |
| 纸面推演会高估 | 诊断报告的"预测涨分"系统性高估,**效果只能由跑测数据裁决**(本项目 V3 预测 80% 实跑 59.4% 方向全错);引入新信号前先验质量(字准率)+确认真注入,脏/空信号比无信号更伤 |
| 修保守用收窄不用删除 | 治"偏保守"用**收窄触发条件**,绝不删整条约束(删=用更大错误覆盖小错误);单 prompt 内多类约束相互耦合时,改走**分阶段双判**(先判 A 类、再对剩余 judge B/C)物理隔离 |
| 数据分析结论禁直接写进 prompt | 分析说"X 仍可判高"→直接加"X 即判高"几乎必然过拟合(rule narrowing)。先由**效果层**抽成与措辞无关的效果,再由**措辞层**落成可复用原则,**永不嵌具体 case/GT 原文**(框架见 `references/prompt-modification.md`) |
| 写前先分流加/删/改 | 每条策略先判型:遗漏→**加原则** / 过具体补丁误伤→**删上抽** / 骨架过严宽→**改触发条件** / 耦合→**隔离**。**先问是加还是删,别默认加**(主病=什么都往里加) |
| CASE_PATCH 拒收 | 一条规则配进 prompt 要过自检:描述类别还是个例?跨≥3 case 复现?删它会不会更短不丢覆盖?只从 1 条 badcase 来的窄规则先存疑、不写 |
| GT 错=轻量前置筛非主精力 | 分流前先问"prompt 问题还是 GT 错";GT 错需四条硬证据(逆序+高置信+二模型同向+COT客观事实)+盲评,真错进 CLAUDE 排除项不改 prompt;**证据不足一律当 prompt 问题**,最后再筛别占主精力 |
| 策略人工对齐=写前闸门(闸门①) | 写提示词前先报"N 条策略",逐条出示(根因+证据+**效果层的效果描述**+**分流类型**+**验收范围**+为什么治+返回率预判),人工逐条批准才动手。审的是方向(该不该追这效果、该加该删),不是措辞——挡**方向**。实际最常拦下的是**假归因**(强行归因 / **跨维度借判据**),出卡前必自检 |
| 写时禁重写(可解释性) | 改提示词默认 **EDIT-局部**(保留原段骨架措辞,只改触发条件/限定词);**禁止 REWRITE-整段**(原段被整段替换/重排)——重写让 §3.5 逐规则 diff 抓不出沉默丢失,是"迭代天翻地覆"根因。耦合型/诊断要求重写须在闸门①策略卡**预标「本段重写+理由」**,否则退回改 EDIT-局部 |
| 提示词验证=写后闸门(闸门②) | 写完派**独立子 agent**(非写 prompt 的自己,防确认偏差)做根因↔diff 双向映射 + **查 case 照搬** + **给每处 diff hunk 打 {ADD/DELETE/EDIT-局部/REWRITE-整段} 标签,未预标的 REWRITE 打回**;漏治/对不准/含 CASE_PATCH/含未预标 REWRITE 不跑测。是 Part4 三分类迁移核验的跑测前镜像——挡**覆盖+可解释性** |
| 三分类归因 xlsx=写后硬验收 | 评测后产 xlsx:①矫正/②未矫正(判能力边界)/③返回(归因到策略,少规则 or 多规则),子 agent 填备注。修正率/返回率只算改动维;净Δ决策、返回率红旗。③类归因回写 CLAUDE 累加 |
| 回归分析=规则级下钻+闸门③ | 三分类 xlsx 的同一步更细颗粒度:**prompt 逐规则 diff 出"消失的旧规定"+ 数据佐证对照 + COT 定位**。专抓「**沉默丢失**」(旧正面规定被无意删、当前数据没暴露)。**闸门③ 晋升 baseline 核查(跑测后)**:发现沉默丢失即便数据更好也不晋升,先找回/论证该删。每轮跑完必做,结论回写 CLAUDE 累加 |
| 迭代后数据分析>单纯迭代 | 跑出新版拿个数字不是终点,三分类迁移+归因才是真产出。这是整条链最值钱的一环 |
| A/B 同口径 | 基线与迭代版必须同样本、同尺子、同运行条件;起码两轮数据;**跨样本集一致率绝对值禁比版本优劣,只许同 nid 同 GT 受控对照** |
| 守止损线 | 跑测中实时监控,触线即该维度回退 |
| 报告交给 report-review | 不内置骨架,定性为"评新增方案+A/B 对照"后让它审 |
| 循环回写文档 | 每轮结束更新 CLAUDE(任务/决策)和 README(工程踩坑) |
| 每 Part 有验收物 | Part0→两份文档;Part1→**机器分析产物(不一致 case 存档+分布/混淆矩阵)+ 策略文档**;Part2→新提示词(**闸门①② 过:策略人工批准 + 根因↔diff映射表**);Part3→推理产物;Part4→**评测产物 + 三分类归因xlsx + 修正率/返回率 + 闸门③ 晋升核查结论 + 报告**。各落 README 约定路径,缺一即该 Part 未完成 |
