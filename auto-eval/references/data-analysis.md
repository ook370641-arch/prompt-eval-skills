# 数据分析环:可复用方法

数据分析是整条迭代链的地基。目的:**找到人评(GT)与当前提示词评分标准的 diff**,从中反推提示词缺陷,得出策略,并预判策略的返回率风险。

## 三条通用铁律

### 1. 从整体到具体

- **先整体**:统计每个维度的偏差方向——**带符号的混淆矩阵**(GT level × Pred level,每条错判标 偏低/偏高 × 跨一档/逆序)、一致率、逆序率、各 diff 类型(中→高/中→低/...)的条数。这张带符号矩阵是下钻的前提:没有它,"主病往哪偏"无从谈起。先定位主病(如"usefulness 主病是过松,中→高 11 条")。
- **读分布相似度定病性**:把 Pred 分布与 GT 分布并排——
  - **分布相似但逐 case 一致率低** → 病性是**判定标准与人不一致**(错判东边一个西边一个、互相抵消了整体分布,整体统计失效),**必须**对具体 case 做更细 diff,不能停在统计层。
  - **分布明显不相似**(模型整体偏向某档) → 病性是提示词**整体偏严/偏宽**,先从被系统性高估/低估的那一档入手。
- **再下钻**:对主病方向的 case,逐条读模型的判定证据,找"模型凭什么这么判 vs GT 凭什么那么判"的分歧点。
- **GT 档位分布是必做的 sanity check**:统计 GT 各档条数。若某档样本极少(如"高"仅 1 条),该维度**实质是二分类**,一致率不能外推到未检验的档;扩容时优先补缺失档,别把偏态分布上的高一致率当成真本事(偏态 GT 会让"近似常数预测器"也拿高分)。

### 2. 收集归因所需的全部辅助证据(不只看 level 对错)

只比"输入→输出 level"无法归因,只能看到"错了",看不到"为什么错"。**必须收集模型的判定过程证据**:

- 带推理链的模型 → **COT / think 段**(根因几乎都藏在这里。例:emotional_value 的"体裁脑补"病,就是从 think 段发现模型在用题材代理情绪价值)。
- 无显式推理 → 中间打分、检索片段、置信度、tags 等任何能反映"模型依据什么"的字段。

**全量分析**:不只看 badcase。"原本判对的 case 模型凭什么判对"同样是信息——它界定了正确策略的边界,也是返回率预判(下条)的对照基准。

**多模型分别归因**:若本轮涉及多个模型(如 Pro/Mini),**绝不合并看**。各跑各的混淆矩阵、各找各的 case 规律——因为 prompt 是"针对某个模型偏置的纠偏器,不是绝对质量物",不同模型偏置方向可能相反,合并看会把两套相反的病性糊成一团。决策与止损也分模型各判一套(不能用 Pro 的成功外推 Mini)。

### 3. 返回率预判

每得出一条策略,追问:**这条新策略会不会把原本判对的 case 改错?**(这是**写前预判**,跑测后由 Part4「返回率实测 + 归因」闭环检验)

- 列出该策略会命中的 case,检查其中原本判对的会不会被带偏。
- 这是 report-review "净收益" 的前置:只治病不顾误伤 = "证明局部有效却没证明值得采用"。预判结果写进 Part1 产出,并在 Part2 闸门一出示给人工批准(每条策略卡的"返回率预判"字段)。
- 典型反例:某项"封顶到中"的排除项治好了过松,却误伤了若干本该判高的优质 case;或"收窄某约束"反而让另一类 case 反弹变差。这些都要在分析阶段就预判,而非跑测后才发现。
- **迭代未见收效 → 回本环再挖,而非急着多生成几版提示词**。"改了没动静/没涨"是上一轮数据分析不够深的信号,**最常见的漏就是没做返回率预判**(治了某批病,却被新策略在原本判对 case 上的误伤精确抵消,净 Δ≈0)。这时该做的是更详尽的逐 case 迁移分析,而不是撞运气式地再产几版。

## 逐 case 迁移核验(基线→迭代版,跑测后必做)

汇总一致率持平 **≠** 没变。净 Δ≈0 常常掩盖大量逐 case 翻转——修对 N 条同时误伤 N 条会精确抵消,只看总分完全看不出。**必须把基线→迭代版的逐 case 变动拆成四类**核验迁移特征:

| 迁移类 | 含义 | 关注点 |
|---|---|---|
| 维持原判·对 | 两版都判对 | 正确策略的稳定盘 |
| 维持原判·错 | 两版都判错 | 本轮没治到的病(下一轮目标) |
| 改对了 | 基线错→迭代对 | 收益来源,记其**方向**(如 中→高 纠回 中→中) |
| 改错了 | 基线对→迭代错 | 误伤/返回率代价,记其**方向** |

净收益 = 改对 − 改错。只有把这四类(及各自方向)理清,才能判断"涨/跌/持平"到底是真效果还是抵消假象。跑测后这张四类表落成 **Part4 的三分类迁移归因 xlsx**(去掉稳定盘"维持对",剩三类:①矫正/②未矫正/③返回),且每类由子 agent 填归因备注——①②判策略成败与能力边界,③做返回归因(哪个策略、少规则还是多规则)。从 xlsx 直接算 **修正率 = ①/(①+②)、返回率(实测) = ③/(③+维持对)**,只算本轮改动维度。

**剥离重跑抖动**:LLM 推理 temperature≠0 时本身有随机性,小样本下一条"翻转"可能根本不是改动引起而是抖动——这是 A/B 最致命的隐藏混杂变量。对结论关键的少数 case,**同输入重跑 3 次取众数**再纳入迁移核验,别把抖动当成收益或退化。

## 产出物

**两件都是 agent 的验收成果,缺一不可——一件靠脚本算、一件靠 agent 分析,后者用前者的数据背书。**

### 1. 脚本算出的结构化分析产物(客观背书)

用一个脚本(本项目 `analyze_all_cases.py`)跑出来,不是 agent 凭印象写:

- **逐 diff case 存档**(jsonl,每行一条):GT level / 模型判定 level / 是否一致 / diff 类型(中→高、中→低…)/ 该 case 对应维度的 **COT 片段**(从 think 段按维度切出)。全量,不只 badcase。
- **整体分布与带符号混淆矩阵**:GT 各档(高/中/低)的分布率、模型判定各档的分布率(两者并排看分布相似度)、`GT×Pred` 混淆矩阵、各 diff 类型条数。

这正是上面铁律 1(整体→具体、带符号混淆矩阵)和铁律 2(读 COT 归因)的**落地产物**——不是额外动作,而是把"必须看分布/矩阵/COT"固化成跑得出、查得到的文件。多模型须分模型各跑一套(不合并)。落 README 约定位置(本项目 `Prompts/V{N}数据分析/`)。

### 2. agent 分析写出的策略文档(由产物 1 背书)

每个目标维度回答:

1. 偏差方向(主病是什么,带混淆矩阵/条数)。
2. 根因(带 COT 证据,说清模型的错误判据 vs GT 判据的分歧点)。
3. **GT 错前置筛**:这条 diff 是 prompt 能治的,还是 GT 本身标错?默认当 prompt 问题;判 GT 错需四条硬证据(逆序非相邻档 + 判官高置信 + 第二独立模型同向 disagree + COT 引用可核验客观事实)+ 人盲评,真错才进 CLAUDE「GT 排除项」、不改 prompt。**证据不足一律当 prompt 问题,GT 错最后再筛别占主精力**。
4. **加/删/改分流 + 提示词策略**:先判型——遗漏→ADD 原则 / 过具体补丁误伤→REMOVE 上抽 / 骨架过严宽→EDIT 触发条件 / 耦合→隔离;再写**与措辞无关的"想要的效果"**(Reflector 产物),**不要把分析结论原文当成待焊入的规则**(那是过拟合源头)。
5. 每条策略的返回率风险(会不会误伤,误伤哪类)。

> 第 3、4 条是防回归的关键,完整框架(Reflector→Refiner、加/删/改决策表、CASE_PATCH 拒收、GT 错证据程序)见 `prompt-modification.md`,本文件只规定"策略文档必须带分流类型 + 想要的效果,不带待焊入的窄规则"。

这份产出要能直接喂 Part2,也要能在 Part4 报告里复用为 badcase 归因表(对齐 report-review §4.5/§4.6)。

> 为什么要机器产物背书:策略文档是叙述性的、可注水——"心算一下分布、扫几条 case"就能声称做了整体分析。有了脚本产出的分布/矩阵/diff 存档,"分析做没做、做到什么深度"就从主观判断变成客观可核验。

## 本项目 example(四维度视频价值标注)

> 以下是本 skill 诞生项目的具体落法,供参照——**不是规定动作**,新项目按自己的数据形态调整。

- **脚本**:`Prompts/BaselineA数据分析/analyze_all_cases.py`。它的核心做法值得复用:
  - 按 nid 索引三类数据:推理结果(含 `think` + `json_output`)、GT、评测打分。
  - 用正则从输出里抽 `<think>...</think>` 和 `<json_output>...</json_output>`。
  - **按维度切分 think 段**(维度一/二/三/四),把每个 badcase 对应维度的推理片段单独提取——这样归因时直接看"模型对这个维度凭什么这么判"。
  - 按维度收集 badcase(score<2)和逆序 case(score=0),统计 diff 类型分布(整体层),再对主病方向做模式分析(具体层),如检查模型是否命中了某"特殊情况捷径"、终止在哪一步、tags 是什么。
  - 产出 `badcase_{dim}.jsonl` 四份,每条带 `think_excerpt`。
- **诊断深化**:本项目还派多个子 agent 对 diff case 做"判据对抗分析"(模型判据 vs GT 判据 vs 分歧定位 vs 方向标签),适用于样本量大、需要并行下钻的场景。
- **返回率预判的真实教训**:V3 的"封顶到中"排除项误伤 6 条手工教程;曾试图收窄这些排除项,结果 usefulness 过松反弹、整体更差。这类"治此伤彼"必须在分析阶段预判。

## → 下一步:交 diagnosis-method 做提示词病因归因

本文件只到"数据现象"这一层:哪档偏了、哪些 case 错了、错向哪、模型 COT 里怎么想的。**现象不等于病因**——"usefulness 中→高 11 条"是现象,"提示词哪个模块/哪一句判据把它判高的"才是病因,后者才是能落成改动的东西。

数据现象产出后(混淆矩阵 + diff 存档 + COT 片段),**接着读 `diagnosis-method.md`** 做提示词层归因:把现象反查到提示词的具体模块/ABC 层(C 层还要看**入参咬合**)、跨版本查**简洁性/规则膨胀**、并按**分桶(模块↔case子集绑定对)**把现象归到各桶、定优先级。data-analysis 是它的输入,不重复算矩阵。
