# 两份项目文档:CLAUDE(spec) / README(plan) 结构模板

启动时读这两份;Part0 时建/改这两份。核心拆分判据:

> **换个工程实现就会变的操作细节 → README;换实现也不变的任务目标/红线 → CLAUDE。**

同一条方法论铁律拆两面写:为什么/红线进 CLAUDE,具体怎么操作进 README,不重复。

---

## CLAUDE.md(spec — 为什么/做什么/红线)

放**项目级、慢变量、换工程实现也不变**的东西。建议结构:

```
# CLAUDE.md
## 项目概述          — 这个项目在做什么、用什么模型、输出什么
## 当前核心任务       — 这一轮迭代在改什么、为什么、当前进行到哪、当前生产版本是谁
## 本轮工作计划       — 目标维度、基线版本、诊断结论、核心洞察(用户指令)、产物清单与流程
## 方法论铁律         — 不可逾越的红线(如"数据分析不读模型推理证据不准出结论"
                       "不做返回率预判不准进跑测""多维度同改必崩,只改隔离维度"
                       "硬止损线:某维度退化>N条即回退"
                       "prompt 是针对特定模型偏置的纠偏器,多模型分别归因/决策/止损"
                       "净Δ≈0可能掩盖逐case翻转,必须拆迁移四类核验"
                       "纸面预测涨分系统性高估,效果只由跑测裁决"
                       "修保守用收窄不删整条约束;耦合维度改分阶段双判"
                       "策略改动须人工逐条批准才动手写提示词"
                       "数据分析结论禁原文焊进prompt,先Reflector抽效果再Refiner落原则,永不嵌case/GT原文"
                       "每条策略先分流加/删/改(遗漏加原则/补丁误伤删上抽/过严宽改触发条件/耦合隔离),先问加还是删别默认加"
                       "GT错=高门槛前置筛非快捷逃生口,需四条硬证据+盲评,证据不足当prompt问题"
                       "评测后必产三分类归因xlsx(矫正/未矫正/返回),算修正率/返回率,返回归因回写CLAUDE累加")
## GT 排除项          — 本轮不拟合的标错标签(nid + 为什么不拟合)
## API/数据格式       — 模型 id、base url、SDK、视频传入方式;推理源/产出/GT 三类 JSONL 的字段schema、评分规则
## 文件目录体系        — 整个项目的目录树 + 每个目录/文件的角色
## 迭代教训(累加!)   — 历史失败版本的复盘结论(防重蹈覆辙);**新一轮只追加不覆盖**
```

> **「迭代教训」必须累加**:每轮新增的失败复盘叠在旧的之上,绝不删旧的。本项目的"四维度同改必崩、崩点恒在 readable""收窄不够须分阶段双判"等血泪结论,丢了就会重蹈覆辙——这是 skill 保留历史迭代经验的核心机制。

要点:CLAUDE 是给"未来的你/下个 session"看的任务上下文。它回答**为什么这么做、什么是红线、现在到哪一步**。

## README.md(plan — 怎么做)

放**工程级操作细节**——具体到读哪个文件、调哪个脚本、填哪个字段。建议结构:

```
# README.md
## 任务背景           — 高颗粒度的任务展开(目标、当前状态、基线指标表)
## 迭代 Pipeline      — 可复用工作流的每一步:数据分析→策略→提示词→跑测→评测→复盘
                       每步:用哪个脚本、输入什么、产出什么、验收标准
## 关键命令           — 可直接复制运行的命令(缓存/Pro 推理/Mini 推理/评测)
## 数据分析硬性要求    — 落地版:必须读哪个 jsonl 的哪个字段(如 think 段)、
                       必须全量 N 条、必须跑返回率预判对照哪批 case、
                       多模型须分模型各算一套混淆矩阵(不合并)
## 技术要点(踩坑)    — 数据通路的坑(视频 base64、landing 页解析、大文件压缩、
                       缓存位置、并发、断点续传、坏缓存 magic-bytes 校验);
                       引入新输入信号(ASR/检索片段/新字段)前须人工抽检质量给字准率/命中率,
                       并确认信号真注入(空/脏信号比无信号更伤,会被重跑抖动伪装成收益)
## 提示词文件格式      — 占位符、标签包裹、输出格式约束(与评测脚本兼容)
## 评测数据匹配        — GT 用什么 key 匹配、评分规则(RANK/分制);
                       GT join 须报命中率+查重;评测产出须含**带符号混淆矩阵**(偏低/偏高×跨档/逆序)
                       与**基线→迭代版逐case迁移四类拆分**(维持对/维持错/改对·方向/改错·方向)
## 评估集分布          — 各测试集多少条、覆盖哪些维度
## 人工核对看板(两版,别混)
  - 写前 GT 复核看板(可选,Part1):单版、跑测前复核 GT 可信度。
    列结构、COT 抽法、生成脚本、产出路径(本项目 docs/{版本}/{维度}核对看板.{xlsx,html})
  - 写后三分类归因 xlsx(硬验收,Part4):两版对比、跑测后迁移归因。
    三类(①矫正/②未矫正/③返回)+ 子 agent 归因备注;列:nid/url/原始COT(迭代)/
    GT/现在结果/原先结果/人工备注;产出路径(本项目 docs/{版本}/ 或 运行与评测/V{N}/)
## 文件产出清单(=验收路径表) — 每个 Part 的验收物落哪个目录、什么命名
```

> **「文件产出清单」就是验收路径表**:它把 skill 主循环里每个 Part 的「✅ 验收物」绑定到本项目的真实目录(docs / Prompts / 运行与评测 / scripts)。skill 只规定"每 Part 必须有验收物、必须落 README 约定的位置";具体落哪个目录、什么命名,由这张表回答。本项目示例:策略→`docs/{版本}提示词策略.md`、提示词→`Prompts/V{N}.md`、推理评测产物→`运行与评测/V{N}/`、报告→`docs/{版本}报告_*.md`、脚本→`运行与评测/scripts/`、写前 GT 复核看板(可选)→`docs/{版本}/{维度}核对看板.{xlsx,html}`、写后三分类归因 xlsx(硬验收)→见 README 约定。

> **两版看板别混**:
> - **写前 GT 复核看板(Part1,可选)**:单版、跑测前、复核 GT 可信度。一行一 case:GT / 各模型判定·分数·偏差 / 各模型判定证据(COT 片段) / 人工备注栏。**"为什么本轮需要人工复核"记在 CLAUDE(红线/盲区),列结构记在 README(操作)**——拆两面写。
> - **写后三分类归因 xlsx(Part4,硬验收)**:两版对比、跑测后迁移归因。三类(①矫正/②未矫正/③返回),子 agent 填归因备注(①②判策略成败/能力边界,③做返回归因——哪个策略、少规则还是多规则);列:nid / url / 原始 COT(迭代版)/ GT / 现在结果(迭代)/ 原先结果(基线)/ 人工备注(留空)。从它直接算修正率/返回率(只算改动维度)。③类返回归因结论回写 CLAUDE「迭代教训」累加。

要点:README 是给"执行这一步的人"看的操作手册。它回答**具体怎么跑、读哪个文件的哪个字段、有哪些坑**。任何"这个项目特有的工程知识"都沉淀在这里,这样 skill 本身才能保持通用。

## 新项目(两份都没有)

**即便没有这两份文档,也先扫一眼文件夹**——现有脚本、历史产物、测试集、过往报告里往往已经藏着目标/基线/数据格式/踩坑的答案。遵循"先吃满上下文、只对盲区盘问"的总原则:能从文件读出的先写进文档,只把**读不出、需用户拍板**的整理成工作清单,用 grill-me 集中对齐。新项目盲区多、要盘的也多,但不等于"全靠问"。

盘问要问到能建起这两份的程度,然后在 Part0:
1. 先建 CLAUDE(把读到的 + 盘出的目标/基线/铁律/目录结构写进去)。
2. 再建 README(把读到的 + 盘出的跑测方式/数据格式/字段/踩坑写进去)。
3. 两份都建好后,才进入 Part1 数据分析。

## 已有项目(改写)

- 读现有两份,理解项目现状。
- 每轮迭代结束:本轮决策/新生产版本/下一步 → 更新 CLAUDE;新发现的工程踩坑 → 更新 README。
- 改写时遵守"surgical changes":只动该动的,不重写无关章节。
