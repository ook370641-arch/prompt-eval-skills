# Prompt 创建 Skill

## Soul：人机协作模式

这个 Skill 的协作方式不是"用户下指令，AI 执行"，而是：

**先定义目标 → 通过模型暴露信息缺口 → 补充决策标准、失败定义和优先级 → 让模型在更清晰的任务框架中工作**

模型不仅是执行者，也可以是帮助用户暴露问题、协助拆解任务的对象。

**关系翻转**：让大模型作为输入方，向你提问，抓取那些为了实现目标所需的信息。

**核心理念**：Prompt 是任务设计的"结果"，不是任务设计本身。从"写prompt"转向"做任务建模"。

---

## 目标

在写 Prompt 之前，先把任务定义、上下游接口、失败容忍度和方案架构定清楚。交付物是一套可以支撑后续迭代和评测的 Prompt 信息栈 + Prompt 文件。

---

## 何时使用

- 新任务刚启动，目标还停留在业务描述层
- 旧 Prompt 改了很多轮，但仍然没有形成稳定方向
- 需要决定继续用单 Prompt，还是拆成多阶段方案、多节点工作流
- 需要把"我脑中想要的效果"翻译成模型能执行、下游能消费的系统设计

## 输出规范

### 输出目录

**默认输出目录**：当前工作目录（用户调用skill时所在的文件夹）

**文件命名规则**：
- Prompt文件：`{任务名}_prompt_v{版本号}.md`
- 设计文档：`{任务名}_prompt_design.md`

**版本递增规则**：
- 如果目录下已存在 `xxx_prompt_v1.md`，则生成 `xxx_prompt_v2.md`
- 永远不覆盖已有文件，始终创建新版本
- 版本号从1开始递增

| 层级      | 错误归因                  |
| ------- | --------------------- |

### Step 3：分轮提问（A→B→C）

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[Step 3/9] 分轮提问
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

⚠️ 进入交互模式 - 等待用户回答
```

**⚠️ 强制交互规则**：
- **必须停下来等待用户回答**，不可自行推断或跳过
- 每个问题单独提出，等待用户回复后再问下一个
- 用户回答后，输出确认收到：`✓ 已收到：[用户回答]`
- 当所有缺失信息都收集完毕后，输出：`✓ 信息收集完成`

**提问原则**：

- 问题之间有连续性：后一个问题承接前一个问题
- 每轮最多 4 个问题
- 动态判断：根据上下文已有信息，只问缺失的部分
- 从 A层（宏观）到 C层（微观）依次进行

**进度输出**：
```
  → 分析已有信息，确定需要补充的内容...
  → 进入第X轮提问（A/B/C层）...
```

**提问依据：Prompt 信息栈（9层）**

| 层级                  | 内容                                  | 关键问题                            |
| ------------------- | ----------------------------------- | ------------------------------- |
| **1. 业务目标**         | 模型最终服务的动作是什么，错误会怎样影响下游              | 这轮唯一想优化的现象是什么？                  |
| **2. 上游输入**         | 图片、题干、历史上下文、规则参数里，真实能给哪些            | 上游真实能给什么输入，哪些输入暂时不可能提供？         |
| **3. 下游输出**         | 字段定义、渲染方式、是否有调试报告、是否允许额外文字          | 下游真正消费哪些字段，哪些字段只是调试信息？          |
| **4. 对象边界**         | 哪些内容属于标注对象，哪些内容必须排除                 | 哪些内容绝对不能标，哪些内容允许漏标但不能错标？        |
| **5. 失败策略**         | 更怕漏标还是更怕错标；哪些场景允许直接放弃输出             | -                               |
| **6. 模型职责**         | 哪些判断必须靠模型完成（语义筛选、关系理解、候选提取）         | -                               |
| **7. 规则职责**         | 哪些内容必须由人先定规则（输出 schema、跨行红线、非法坐标过滤） | -                               |
| **8. bad case 优先级** | 当前最值得修的失败类型是什么，不要同时优化所有问题           | 这轮 bad case 的优先级是什么，是否已有固定判定样本？ |
| **9. 评测表面**         | 这轮怎么验证生效，观察哪些 case、哪些字段、哪些副作用       | -                               |

**没有这九层，Prompt 只是措辞；有了这九层，Prompt 才是任务建模结果。只有Prompt所需信息收集完整，工作才准许开始。**

#### 第一轮：A层（任务定义层）

**连续性设计**：目标 → 用途 → 标准 → 优先级

| 序号  | 问题                      | 目的            | 对应信息栈     |
| --- | ----------------------- | ------------- | --------- |
| A1  | 模型最终要产出什么？（输出形式、字段、格式）  | 明确目标          | 业务目标      |
| A2  | 这个产出用来做什么？谁会消费它？        | 理解用途，帮助定义"好坏" | 业务目标、下游输出 |
| A3  | 什么情况算成功？什么情况算失败？        | 定义具体标准        | 业务目标、失败策略 |
| A4  | 如果有冲突（如漏标 vs 错标），优先保哪个？ | 明确取舍原则        | 失败策略      |

**信息完整判断**：

- 目标：有明确的输出形式（JSON/文本/列表），不是模糊描述
- 标准：有具体的判定条件，不是"效果好"这种模糊词
- 优先级：有明确的取舍原则

#### 第二轮：B层（任务拆分层）

**连续性设计**：输入 → 核心输入 → 输出 → 拆分

| 序号  | 问题                            | 目的        | 对应信息栈       |
| --- | ----------------------------- | --------- | ----------- |
| B1  | 上游能提供什么输入？（文本/图片/结构化数据/历史上下文） | 明确输入边界    | 上游输入        |
| B2  | 输入中有哪些是必须用的？哪些是可选的？           | 区分核心和辅助输入 | 上游输入        |
| B3  | 下游需要哪些字段？哪些只是调试用？             | 明确输出边界    | 下游输出        |
| B4  | 是否允许拆成多阶段？还是必须单 Prompt？       | 决定拆分方案    | 模型职责 + 规则职责 |

**信息完整判断**：

- 输入：知道哪些可用、哪些不可用
- 输出：知道哪些字段是生产必须、哪些是调试
- 拆分：有明确的决策（单阶段/多阶段）

#### 第三轮：C层（规则下沉层）

**连续性设计**：边界 → 红线 → 规则 → 优先级

| 序号  | 问题                        | 目的     | 对应信息栈 |
| --- | ------------------------- | ------ | ----- |
| C1  | 哪些内容属于处理对象？哪些必须排除？        | 明确处理边界 | 对象边界  |
| C2  | 有哪些绝对不能做的事？（红线约束）         | 明确禁止项  | 规则职责  |
| C3  | 有哪些必须遵守的具体规则？（如格式、顺序、优先级） | 明确执行规则 | 规则职责  |
| C4  | 这些规则之间有优先级吗？冲突时怎么处理？      | 规则排序   | 规则职责  |

**信息完整判断**：

- 边界：有明确的包含/排除标准
- 红线：有具体的禁止项列表，或明确无禁止
- 规则：有可执行的规则描述，不是"要准确"这种模糊词

### Step 5：方案决策报告

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[Step 5/9] 方案决策
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

在写 Prompt 前，先做方案决策，判断这个任务适合怎么处理。

**进度输出**：
```
  → 分析模型与规则分工...
  → 判断方案选择...
  → 生成决策报告...
```

#### 执行顺序

**先判断：模型与规则分工 → 再判断：方案选择**

#### 第一步：模型与规则分工判断

**判断原则**：这件事是否需要语义理解？如果不需要，优先做规则。

**适合交给模型的内容**：

- 语义筛选
- 关系判断
- 软判断

**适合交给规则的内容**：

- 输出格式与字段枚举
- 合法性约束
- 可用代码等其他技术栈处理的明确红线、各类硬约束

#### 第二步：方案选择判断

**判断流程**：

```
模型负责的部分是否可单段Prompt覆盖？
    ├─ 是 → 单段 Prompt
    ├─ 否 → 多阶段 Prompt
    └─ 有大量规则/代码部分 → Prompt + 其他工具栈混合
```

**单段 Prompt 条件**：

- 输出结构简单
- 任务耦合度低
- 预测Prompt可有效输出所需下游

**多阶段 Prompt 条件**：

- 依据大模型能力边界与功能序列判断，当前任务内嵌适合代码等其它工具处理的任务
- 多任务耦合，极可能造成输出不稳定

**Prompt + 其他工具栈混合**：当问题本质上是结构问题，而不是理解问题时，不要继续加 Prompt。直接把这部分下沉成规则或后处理，并建议使用其他工具栈处理。

#### 输出方案决策报告

```
方案决策报告：

1. 模型与规则分工：
   - 模型负责：[语义筛选、关系判断...]
   - 规则负责：[输出格式、坐标约束...]

2. 方案选择：
   - [ ] 单段 Prompt
   - [ ] 多阶段 Prompt
   - [ ] Prompt + 其他工具栈混合

3. 决策理由：
   [说明为什么选择这个方案]
```

✓ Step 5 完成：已确定方案方向

### Step 6：生成Prompt

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[Step 6/9] 生成Prompt
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

#### Step 6.1：打包全量信息

将以下内容整理成结构化输入：

- 信息栈（9层）：业务目标、上游输入、下游输出、对象边界、失败策略、模型职责、规则职责、bad case优先级、评测表面
- ABC层任务理解

**进度输出**：
```
  → 打包信息栈（9层）...
  → 整合ABC层理解...
```

#### Step 6.2：调用子agent生成Prompt

**⚠️ 子agent可见性规则**：
- 调用前必须展示传给子agent的内容摘要
- 调用后必须展示子agent的产出摘要
- 用户应能判断子agent是否正确执行了任务

**进度输出**：

│ - 执行流程：已包含                                      │
│ - 规则：已包含                                         │
└─────────────────────────────────────────────────────┘
```

**传给子agent的内容**：

```
依据以下信息，一步一步撰写结构化的提示词，来符合下游产出要求。

【打包信息】
[信息栈 + ABC层理解]

【撰写顺序】
1. 任务情境：下游如何消费结果、错误会造成什么后果（不是角色表演）
2. 输入输出定义：字段、格式、结构（先锁定再写流程）
3. 红线约束：一旦出错就会污染结果的约束（前置）
4. 明确执行流程：先筛选 → 再定位 → 再自检（按执行顺序，不打散）
5. 确立规则：只保留真正影响行为的规则（不堆复盘感想）

**子agent入参**：打包信息 + 撰写顺序 + 起始指令

**子agent出参**：Prompt文本

**不应提供给子agent**：

1. 全量历史 Prompt 原文

4. 对某个版本的主观印象式评价

### Step 7：检验Prompt质量

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[Step 7/9] 检验Prompt质量
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

#### Step 7.1：检验方法

逐项对比打包信息，检验prompt是否能够结构分明地完成打包信息里定义的任务需求。

**进度输出**：
```
  → 检验信息覆盖...
  → 检验结构清晰度...
  → 检验执行可行性...
  → 检验一致性...
```

#### Step 7.2：检验维度

| 维度       | 检验内容                      | 检验方式                           |
| -------- | ------------------------- | ------------------------------ |
| **信息覆盖** | 打包信息里的每个需求是否都在prompt中有对应？ | 逐项对照信息栈（9层）+ ABC层理解，检查是否有遗漏    |
| **结构清晰** | prompt是否结构分明，能够满足下游产出要求？  | 对照下游输出要求，检查撰写顺序是否清晰、逻辑是否连贯     |
| **执行可行** | prompt里的规则是否可执行？          | 检查是否有模糊词（"要准确"、"尽量"）、是否有具体判断条件 |
| **一致性**  | prompt内部是否有冲突指令？          | 检查规则之间是否矛盾、优先级是否明确             |

#### Step 7.3：检验结果

- **通过**：prompt结构分明地覆盖了所有打包信息
- **不通过**：附问题点（哪个需求遗漏 / 哪个规则不可执行 / 哪里有冲突 / 结构是否清晰）

✓ Step 7 完成：检验通过/不通过（附问题点）
